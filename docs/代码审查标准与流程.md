# 代码审查标准与流程

> 版本 **v1.0** ｜ 生效日期 2026-10-05 ｜ 适用范围：`110` 项目全部代码
> 本文是团队代码审查的**唯一权威来源**。与本文冲突的个人习惯，以本文为准。

---

## 0. 一页速览

| 项 | 约定 |
| --- | --- |
| 审查目标 | 拦住**缺陷**、传递**知识**、守住**一致性**——不是评判人 |
| 适用范围 | 所有进入 `main` 的代码；文档、配置、SQL 迁移、CI 脚本**同等适用** |
| 阻断项 | 安全、数据/并发、正确性三类中的 P0/P1 问题 |
| PR 规模上限 | **400 行有效改动**（不含 lockfile / 生成物）；超过须拆分或预约专题审查 |
| 首次响应时限 | P0 立即；P1 4 小时；P2/P3 1 个工作日 |
| 合入条件 | 2 个批准（含 1 名领域负责人）+ CI 全绿 + 无未决 P0/P1 |
| 强制门禁 | EditorConfig → 本地 hooks → CI → 人工审查（**四层，缺一不可**） |
| 本文修订 | 每次回顾会（每 2 周）评估一次；有 2 次以上同类问题重复出现即固化为规则 |

## 1. 审查目标与适用范围

### 1.1 目标（可度量）

| # | 目标 | 度量指标 | 目标值 |
| --- | --- | --- | --- |
| G1 | **拦截缺陷** | 逃逸到 `main` 之后才发现的缺陷数 | 每月 ≤ 2 |
| G2 | **统一一致性** | 因「风格/结构分歧」产生的返工 PR 数 | 每月 ≤ 1 |
| G3 | **传递知识** | 每个模块至少有 **2 人**能独立修改 | 6 周内达成 |
| G4 | **可持续** | 单 PR 从提交到合入的中位时长 | ≤ 8 工作小时 |

> **明确不做**：审查不用于考核个人绩效，不作为「谁写得多」的评比依据。审查意见针对**代码**，不针对**人**。这条不是口号——它是让作者愿意暴露问题、而不是隐藏问题的前提。

### 1.2 适用范围

**必须审查**（无例外）：

- 所有进入 `main` 的源码变更
- **数据库迁移 SQL**（含 `CHECK` 约束、索引、外键）
- `Dockerfile` / `docker-compose.yml` / Nginx 配置
- CI 配置、构建脚本、`.env.example`
- 权限判定、状态机、幂等/并发相关代码（**强制双人审查**）

**可豁免**（走轻量流程，仍需 1 人批准）：

- 纯文档（`docs/**.md`、`README.md`）—— 但若描述与代码行为不符，按 P2 处理
- lockfile 变更（`package-lock.json`）—— 但**必须**确认 `package.json` 与 lockfile 同步
- 自动生成物（`dist/`、`node_modules/`）—— 本不应入库，见 §3.E

**不受理**（审查前先解决）：

- 未通过 CI 的 PR
- 未写清「改了什么 / 为什么改 / 怎么验」的 PR
- 单次超过 400 行有效改动的 PR（除非提前预约专题审查）

### 1.3 边界（防止审查膨胀）

审查者**不**负责：

- 替作者重写代码（可以给建议，不接管）
- 判断产品需求是否合理（那是需求评审的事）
- 检查与本 PR 无关的历史遗留问题（**记录下来另开 issue**，不在本 PR 里要求修复）

## 2. 角色与职责

### 2.1 角色定义

| 角色 | 职责 | 关键产出 |
| --- | --- | --- |
| **作者 Author** | 自检、拆分 PR、写清描述、响应意见、修复问题 | 可审查的 PR |
| **审查者 Reviewer** | 按 §3 逐项检查、给出**可执行**的意见、区分阻断/建议 | 审查结论（批准/要求修改/拒绝） |
| **领域负责人 Domain Owner** | 对核心领域（权限、状态机、并发、迁移）做**终审** | 关键模块的批准 |
| **合入者 Integrator** | 确认门禁全绿后执行合入 | 合入记录 |
| **质量守护 Quality Keeper** | 维护本标准的有效性、统计度量、主持回顾 | 度量报表 + 标准修订 |

### 2.2 小团队的角色合并规则

团队规模 3~8 人时，**允许一人多角，但必须满足两条硬约束**：

| 约束 | 说明 |
| --- | --- |
| **作者 ≠ 审查者** | 任何人都不得批准自己的 PR。这是唯一不可合并的规则。 |
| **核心代码至少 2 人看过** | 权限、状态机、并发、迁移四类，须「作者 + 1 名领域负责人」，不能只由同一位同事轮转批准 |

角色分配建议（以 5 人团队为例）：

| 成员 | 角色组合 |
| --- | --- |
| A（技术负责人） | 领域负责人（权限/并发/迁移）+ 质量守护 |
| B、C | 审查者（轮流，避免固定配对形成盲区） |
| D | 审查者 + 合入者 |
| E | 作者为主，逐步承担审查 |

> **反模式警示**：固定「A 写、B 审」的配对会让两人的共同盲区变成系统的盲区。**每 4 周轮换一次配对关系**。

### 2.3 审查者的责任边界

审查者**必须**：

- 在时限内响应（§5.2）
- 对每个问题给出：**位置 + 现象 + 影响 + 建议方向**
- 明确区分「必须改」（P0/P1）与「建议改」（P2/P3），不把个人偏好包装成阻断项

审查者**不得**：

- 用「我觉得不好」这类无法执行的表述作为阻断理由
- 在 P0/P1 上妥协（「这次先这样，下次注意」→ 会变成永久技术债）
- 要求作者修改与本 PR 目标无关的代码

## 3. 检查项与判定标准

### 3.0 分级原则

| 级别 | 含义 | 是否阻断合入 |
| --- | --- | --- |
| **阻断项（Blocker）** | 违反安全 / 数据完整性 / 正确性 / 领域约束 | ✅ 必须修复 |
| **建议项（Suggestion）** | 可读性、风格、优化空间 | ❌ 不阻断，但须记录 |

**判定方法**：每类检查项给出「通过标准」与「不通过标准」。**能写出反例的才算判定标准**，写不出反例的是个人偏好，不得作为阻断依据。

---

### A. 正确性与领域一致性

| 检查项 | 通过标准 | 不通过标准（反例） |
| --- | --- | --- |
| A1 领域规则单一落点 | 状态、权限、不变量只在 `domain/` 定义一次 | 在 controller/service 里重新写一遍 `if (state === 'PENDING')` |
| A2 状态枚举封闭 | 状态取值由类型 + 数据库 `CHECK` 双重约束 | 用裸字符串 `'pending'`（大小写不一致） |
| A3 角色判定 | 角色从**资源行**现场推导（`roleOf`） | 从用户全局属性判断「是不是负责人」 |
| A4 一命令一事件 | 一次成功的领域命令恰好产生一条 `EVENT`，且 `seq = row_version` | 状态变了但没写事件；或写了事件但状态没变 |
| A5 冻结语义 | 开始处理后正文与验收条件不可改 | 编辑接口只判断「是不是提出者」，漏判状态 |
| A6 追加式历史 | 提交/验收记录只新增，不更新不删除 | 用 `upsert` 覆盖历史提交 |

**A 类实例（本仓库首轮实审）**

> `backend/src/pipeline/command-pipeline.ts:76` —— 过期页面保护被写成可选：
> ```ts
> if (expectedRowVersion !== undefined && pre.rowVersion !== expectedRowVersion)
> ```
> 客户端不传 `If-Match` 时，整段校验被跳过。虽然事务内 `conditionalUpdate` 仍用最新版本避免了丢更新，但「旧页面操作必须被拒」这一**领域语义**可被绕过。→ 判定为 **P1（A1/A4 相关）**。

---

### B. 安全性

| 检查项 | 通过标准 | 不通过标准（反例） |
| --- | --- | --- |
| B1 身份来源 | 操作者一律取自**服务端会话** | 接受请求体/查询参数传入的 `actorId`、`userId` |
| B2 授权位置 | 后端强制校验；前端隐藏按钮仅为体验优化 | 仅靠前端不渲染按钮来限制权限 |
| B3 防枚举 | 对无权知道的资源返回 `404`；对可见但越权的动作返回 `403` | 对无关资源返回 `403`（泄露「该资源存在」） |
| B4 错误信息 | 4xx 不含堆栈 / SQL / 内部 ID；账号不存在与密码错误**返回同一提示** | `throw new Error(err.stack)` 直接回传 |
| B5 凭据管理 | 密钥仅经服务端环境变量注入；仓库内无真实密钥 | `.env` 入库；密钥硬编码在前端 |
| B6 会话 | `httpOnly` + `sameSite`；登出服务端立即失效 | 把 token 存 `localStorage` |
| B7 输入校验 | 应用层用**真解析器**（如 `new URL()`），数据库约束仅兜底 | 只用正则校验 URL，或完全不校验 |
| B8 依赖 | 无已知高危漏洞（`npm audit --omit=dev` 无 critical/high） | 引入已废弃且无维护的包 |

**B 类判定要点**：「前端已经限制了」**永远不是**通过理由。判据是「直接构造 HTTP 请求能否绕过」。

---

### C. 数据与并发

| 检查项 | 通过标准 | 不通过标准（反例） |
| --- | --- | --- |
| C1 乐观锁 | `row_version` + 条件更新，且校验 `count === 1` | 「先查询再更新」（读-改-写之间有竞态窗口） |
| C2 版本号递增 | 与业务变更在**同一条 SQL** 完成（`increment`） | 应用层算出新值再 `set`（并发下会覆盖） |
| C3 幂等原子性 | 幂等占坑与业务变更**同一事务** | 先提交业务再写幂等记录（崩溃窗口 → 重复业务） |
| C4 幂等指纹 | 稳定序列化（对象键排序）后哈希 | 直接 `JSON.stringify`（键顺序不同 → 误判冲突） |
| C5 事务边界 | 事务内不发起网络/文件 IO；不跨事务持有状态 | 在事务里调用外部 HTTP 接口 |
| C6 迁移可回放 | 迁移幂等、可重复执行；含必要 `CHECK`/索引/外键 | 手写 SQL 漏掉外键；改列名不留兼容路径 |
| C7 索引 | 高频筛选字段有索引（如 `(proposer_id, state)`） | 全表扫描的列表查询 |
| C8 N+1 查询 | 关联数据用 `include`/`select` 一次取回 | 循环里逐条查询 |

**C 类实例（本仓库首轮实审）**

> `backend/prisma/migrations/0001_init/migration.sql:46` —— `requirement.current_submission_id` **没有外键约束**（推测因 `requirement ↔ submission` 循环依赖而被省略）。数据库层无法阻止悬空指针，一旦指向已删除的提交，「当前提交不可验收」会变成 `404` 而非明确错误。→ 判定为 **P2（C6）**，修复方式见 §附录 B。

---

### D. 可读性与命名

| 检查项 | 通过标准 | 不通过标准（反例） |
| --- | --- | --- |
| D1 命名表意 | 名字说明「是什么」而非「怎么算」；布尔用 `is/has/can/should` 前缀 | `data`、`tmp`、`flag`、`list2`、`handleThing` |
| D2 函数长度 | 单函数 ≤ 50 行；嵌套 ≤ 4 层 | 200 行函数、8 层 `if` 嵌套 |
| D3 注释解释「为什么」 | 注释说明**取舍原因**与**陷阱** | 注释复述代码（`i++ // i 加一`）；或干脆无注释 |
| D4 注释与代码一致 | 注释描述与实现行为完全吻合 | **注释说 A，代码做 B**（比无注释更有害） |
| D5 魔法值 | 常量集中定义（如 `LIMITS.TITLE_MAX`） | 散落的 `200`、`'PENDING'` 字面量 |
| D6 死代码 | 无未使用变量、无注释掉的代码块 | 大段 `// TODO: 删除` 的历史代码 |

**D 类实例（本仓库首轮实审）**

> `frontend/src/api.ts:168-171` —— 注释写「**412（并发冲突）与 409（状态冲突）** 需要提示用户刷新后重试」，但实现是：
> ```ts
> return err instanceof ApiError && (err.status === 412 || err.code === 'PRECONDITION_FAILED');
> ```
> **不含 409**。注释与代码不一致，会误导后续维护者以为 409 已被处理。→ 判定为 **P3（D4）**。

### E. 代码规范与风格

| 检查项 | 通过标准 | 不通过标准（反例） |
| --- | --- | --- |
| E1 格式化 | 由 Prettier 自动决定，**不在评审中讨论空格/换行** | 手工调整缩进、争论分号 |
| E2 静态检查 | ESLint 零 error | 靠 `eslint-disable` 压掉告警而不写原因 |
| E3 类型 | `strict: true`；无 `any`（必须用时写明理由） | `as any` 绕过类型系统 |
| E4 行尾 | 仓库内统一 **LF**，由 `.gitattributes` 强制 | Windows 克隆出 CRLF 导致容器内 `$'\r': command not found` |
| E5 编码 | UTF-8 无 BOM | 混合编码导致中文乱码 |
| E6 依赖 | lockfile 与 `package.json` 同步；有 lockfile 时用 `npm ci` | 只改 `package.json` 不改 lockfile → `npm ci` 直接失败 |

> **E 类的实现方式**：全部交给工具，**不占用人的审查带宽**。人在 E 类上唯一的职责是确认「工具已经跑过且通过」。

### F. 性能与资源

| 检查项 | 通过标准 | 不通过标准（反例） |
| --- | --- | --- |
| F1 查询规模 | 列表接口有分页或明确上限 | 无条件 `findMany()` 返回全表 |
| F2 索引命中 | 筛选/排序字段有索引支撑 | `WHERE` 走全表扫描 |
| F3 循环内 IO | 批量操作用 `createMany` / `in` 查询 | 循环内 `await` 单条写入 |
| F4 前端体积 | 路由级代码分割（懒加载）；单 chunk ≤ 500 kB | 首屏加载全部页面 |
| F5 缓存 | 带哈希的静态资源长缓存；API 不误缓存 | 动态接口被 CDN 缓存 |

**判定要点**：本项目的规模下，**F 类不追求极致优化**。只有当「数据量增长 10 倍会出问题」时才判定为阻断；否则记为建议项。

### G. 测试覆盖

| 检查项 | 通过标准 | 不通过标准（反例） |
| --- | --- | --- |
| G1 新增逻辑有测试 | 新增/修改的**判定逻辑**有对应测试 | 只测 happy path |
| G2 边界用例 | 覆盖空值、超长、越权、并发、重复提交 | 只测「正常输入 → 正常输出」 |
| G3 断言有效性 | 断言具体行为与状态码 | `expect(true).toBe(true)` 式假测试 |
| G4 测试可重复 | 不依赖执行顺序、不依赖真实时间 | 用 `sleep(1000)` 等待异步 |
| G5 测试与代码同 PR | 测试随功能一起提交 | 「测试下个 PR 补」 |

**最低要求（本项目）**：以下四类**必须**有测试——

1. **权限**：无关账号 404、越权 403、状态不符 409、未登录 401
2. **并发**：旧版本号提交 → 412；同幂等键重放 → 回放原响应
3. **不变量**：退回无原因 → 422；有未通过项点完成 → 422
4. **状态机**：全部合法流转 + 全部非法流转被拒

> **当前状态：G 类为 0 分。** 仓库内**没有任何测试文件**。这是本项目最大的质量缺口，也是「代码质量参差不齐」的核心成因——没有客观门禁，正确性只能靠人工验证，而人工验证不可重复、不可回归。→ 判定为 **P1**。

### H. 可运维性

| 检查项 | 通过标准 | 不通过标准（反例） |
| --- | --- | --- |
| H1 错误出口统一 | 所有异常经统一过滤器，响应格式一致 | 有的接口回 `{message}`，有的回 `{error}` |
| H2 日志 | 5xx 记服务端日志含上下文；4xx 不刷屏 | 用 `console.log` 打业务数据（含敏感信息） |
| H3 健康检查 | 提供真实探测依赖的健康接口 | 返回固定的 `{"status":"ok"}` |
| H4 配置外部化 | 全部配置项有默认值 + `.env.example` 说明 | 硬编码端口、连接串 |
| H5 启动幂等 | 重复启动不产生重复数据、不覆盖已有数据 | seed 用 `create` 导致重启后数据翻倍 |
| H6 数据持久化 | 业务数据落在命名卷；容器重建后仍可读 | 数据存在容器可写层 |

## 4. 审查流程

### 4.1 七步流程

```
① 准备          ② 自检          ③ 提交            ④ 分流
拆分支+定目标 → 作者自查清单 → 开 PR 写描述 → 按规模/风险定审查强度
                                                    │
                                        ┌───────────┴───────────┐
                                        ▼                       ▼
                                  轻量流程                  标准流程
                              (文档/配置, 1人)          (代码, 2人+领域负责人)
                                        │                       │
                                        └───────────┬───────────┘
                                                    ▼
⑤ 审查          ⑥ 反馈              ⑦ 合入
逐项对照 §3 → 分级+定时限 → 门禁全绿后合入 → 回顾沉淀
```

### 4.2 各环节准入 / 准出条件

| 环节 | 准入条件 | 准出条件 |
| --- | --- | --- |
| ① 准备 | 目标明确、可独立回滚 | 分支从最新 `main` 切出 |
| ② 自检 | — | 附录 A 清单**逐项**勾选；本地 `build` + `typecheck` 通过 |
| ③ 提交 | 自检完成 | PR 描述含：**改了什么 / 为什么 / 怎么验 / 风险点** |
| ④ 分流 | PR 已开 | 确定审查者（作者不可选自己）、确定是否需领域负责人 |
| ⑤ 审查 | CI 全绿 | 每个问题已分级；结论明确（批准/要求修改/拒绝） |
| ⑥ 反馈 | 收到意见 | 作者逐条回应：修复 / 说明理由 / 记为后续 issue（P2/P3 可后置） |
| ⑦ 合入 | 无未决 P0/P1；批准数达标；CI 绿 | 使用 **Squash merge**，提交信息符合 §6.3 |

### 4.3 PR 规模控制

| 有效改动行数 | 处理方式 |
| --- | --- |
| ≤ 150 | 正常审查，建议 30 分钟内完成 |
| 151 ~ 400 | 正常审查，需明确审查者时间窗 |
| > 400 | **必须拆分**；若确实无法拆分（如大迁移），**提前预约专题审查**并预告 1 小时 |

> **为什么限制规模**：超过 400 行后，审查者的缺陷检出率**显著下降**，而批准率反而上升（「太长不看，先批了」）。这是认知负荷的硬限制，不是态度问题。

## 5. 问题分级、处理时限与升级

### 5.1 分级定义

| 级别 | 定义 | 典型示例 | 是否阻断 | 处理时限 |
| --- | --- | --- | --- | --- |
| **P0 严重** | 安全漏洞、数据丢失/损坏、生产不可用 | 越权可读他人数据；迁移会删数据；密钥入库 | ✅ 立即阻断 | **立即**（当天必须修复） |
| **P1 高** | 领域约束被绕过、并发缺陷、核心逻辑错误 | 乐观锁可被跳过；幂等不原子；终态可被推进 | ✅ 阻断 | **1 个工作日** |
| **P2 中** | 可维护性/健壮性问题，暂不影响正确性 | 缺外键；缺索引；异常未兜底 | ❌ 不阻断 | **本迭代内**（≤ 5 工作日） |
| **P3 低** | 风格、命名、注释、优化建议 | 注释与代码不符；命名不表意 | ❌ 不阻断 | **下个迭代**或记为技术债 |

### 5.2 响应与修复 SLA

| 阶段 | P0 | P1 | P2 | P3 |
| --- | --- | --- | --- | --- |
| 审查者**首次响应** | 30 分钟内 | 4 小时内 | 1 个工作日 | 2 个工作日 |
| 作者**修复** | 当天 | 1 个工作日 | 5 个工作日 | 下个迭代 |
| 审查者**复审** | 1 小时内 | 4 小时内 | 2 个工作日 | 不强制复审 |

> **超时升级**：P0/P1 超时未响应 → 自动升级至技术负责人；连续 2 次超时 → 在回顾会复盘流程瓶颈（而不是追责个人）。

### 5.3 争议升级路径

```
作者与审查者意见分歧
      │
      ├─ 是「风格/偏好」问题？ ──→ 交给工具决定（Prettier/ESLint），讨论立即终止
      │
      ├─ 是「事实」问题？ ──→ 用证据裁决：写一个最小复现（测试/脚本），跑出来看
      │
      └─ 是「取舍」问题？ ──→ 领域负责人裁决，并记录为 ADR
                              （决策 + 理由 + 反转条件，写入 docs/adr/）
```

**原则**：**能用证据解决的，不用讨论解决；能用工具解决的，不用人解决。** 争论超过 15 分钟无结论，直接升级。

#### 6.3.1 `main` 的必需状态检查（交付验收项）

「禁止直接 push 到 main」这句话只有在 **GitHub 侧真的配了分支保护**时才成立 ——
仓库里的文档约束不了 GitHub。因此把「已配置分支保护」写成**验收项**，确保它不被遗忘。

`main` 的 required status checks 必须**恰好**是这 6 个（对应 `.github/workflows/ci.yml` 的 6 个 job）：

| # | 检查名（job `name`） | 挡住什么 |
| --- | --- | --- |
| 1 | `仓库卫生（行尾 / 密钥 / 构建产物 / lockfile）` | 行尾 / 密钥入库 / 构建产物入库 / lockfile 不同步 |
| 2 | `后端（Prisma 校验 + 构建）` | schema 语法与格式、构建、Prettier、ESLint、单元测试 |
| 3 | `前端（类型检查 + 构建）` | 类型检查、构建、Prettier、ESLint、单元测试 |
| 4 | `迁移可回放性` | 已应用迁移被改（C3）、schema↔迁移漂移（C2）、空库重放、15 条 CHECK 约束 |
| 5 | `端到端（起服务 + DEM-00~08 + DEM-11~16）` | 只在服务真跑起来时才暴露的跨层缺陷 |
| 6 | `Compose 配置校验` | `docker-compose.yml` 语法与变量插值 |

同时要求：

- ☑ **Require branches to be up to date before merging**（避免「各自绿、合起来红」）
- ☑ **Require a pull request before merging**，且至少 1 个 approve（小团队下由非作者审）
- ☑ **Do not allow bypassing the above settings**（管理员同样受约束）
- ☐ 不勾 **Allow force pushes** / **Allow deletions**

> **为什么是「恰好这 6 个」**：required checks 写多或写少都会出问题 ——
> 漏掉一个，那条门禁就只是「建议」；多写一个不存在的名字，GitHub 会永远等待一个
> 永不出现的检查，PR 永久卡住。**CI 增删 job 时，这份清单必须同步更新**，
> 这也是把它写进文档而不是只配在界面上的原因。
>
> ⚠️ **本项的验证限度**：仓库内的文档无法证明 GitHub 侧已配置。要确认请打开
> `Settings → Branches → Branch protection rules` 逐条核对上表。
> 交付验收时应由管理员截图或当场核对，而不是「文档写了就算做了」。

### 6.4 度量指标（每月统计，用于改进而非考核）

| 指标 | 计算方式 | 健康区间 |
| --- | --- | --- |
| 审查覆盖率 | 经审查合入的 PR / 全部合入 PR | **100%** |
