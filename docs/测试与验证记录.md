### DEM-07 重复 / 过期 / 终态操作

> **⚠️ 本节预期已按代码语义修正。** 初稿把「同一 `Idempotency-Key` 重复提交」的预期写成
> 「两次响应完全一致（回放首次结果）」。走查 `command-pipeline.ts` 后确认该预期**不成立**：
> 事务外的 `assertCanPerform`（角色 → 状态守卫）与版本校验在**幂等占坑之前**执行，
> 而 `SUBMIT` 成功后会离开它被允许的状态（`IN_PROGRESS → IN_REVIEW`），
> 因此重复请求会先被状态守卫拒绝（**409**），根本走不到「回放已落库响应」那一步。
>
> 结论：**回放路径对「执行后会改变状态的命令」不可达**，只对 `CREATE`（无状态/版本守卫）
> 以及「执行后状态仍允许该动作」的场景（如 `PENDING` 下的 `EDIT`）可达。
> 但幂等的**实质保证仍然成立**——重复请求绝不会产生第二条业务记录。
> 故本节改为以「不产生第二条业务记录」作为断言，并在脚本中把状态码差异列为**观察项**。

```bash
# ① 幂等：同一 Idempotency-Key 重复请求 → 只产生一次业务记录
#    用 CREATE 验证回放路径（CREATE 无状态与版本守卫，回放可达）
curl -s -b $JA -X POST http://localhost:8080/api/requirements \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: dem07-idem' \
  -d '{"title":"幂等验证","description":"验证同键只创建一次","assigneeId":"00000000-0000-4000-8000-000000000002","criteria":["条件一"]}' > /tmp/r1.json
curl -s -b $JA -X POST http://localhost:8080/api/requirements \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: dem07-idem' \
  -d '{"title":"幂等验证","description":"验证同键只创建一次","assigneeId":"00000000-0000-4000-8000-000000000002","criteria":["条件一"]}' > /tmp/r2.json
diff /tmp/r1.json /tmp/r2.json && echo '两次响应完全一致（回放首次结果）'
# 预期：两次均 201，响应体完全相同（同一个 id），数据库中只新增 1 条需求

# ② 同键不同载荷 → 409
curl -s -b $JA -X POST http://localhost:8080/api/requirements \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: dem07-idem' \
  -d '{"title":"幂等验证（载荷不同）","description":"验证同键只创建一次","assigneeId":"00000000-0000-4000-8000-000000000002","criteria":["条件一"]}'
# 预期：409（IDEMPOTENCY_KEY_REUSED）

# ③ 重复提交（状态已改变）→ 被守卫拒绝，但不得产生第二条记录
curl -s -b $JB -o /dev/null -w '%{http_code}\n' -X POST http://localhost:8080/api/requirements/$RID7/submissions \
  -H 'Content-Type: application/json' -H "If-Match: $V" -H 'Idempotency-Key: dem07-dup' \
  -d '{"artifacts":["https://example.com/dup"],"note":"重复请求测试"}'
# 第一次：201
# 第二次（同键同载荷同版本）：409（状态守卫先于幂等占坑）
curl -s -b $JA http://localhost:8080/api/requirements/$RID7/history | grep -c '"submissionNo"'
# 预期：1（重复请求未产生第二条提交记录）—— 这才是幂等的实质保证

# ④ 终态后再次退回 → 不改变状态、不产生虚假历史
curl -s -b $J -o /dev/null -w '%{http_code}\n' -X POST http://localhost:8080/api/submissions/$SID2/reviews \
  -H 'Content-Type: application/json' -H 'If-Match: 7' -H 'Idempotency-Key: dem07-final' \
  -d "{\"action\":\"RETURN\",\"reason\":\"终态后退回\",\"checks\":[{\"criterionId\":\"$C1\",\"passed\":false},{\"criterionId\":\"$C2\",\"passed\":false},{\"criterionId\":\"$C3\",\"passed\":false}]}"
# 预期：409，状态仍为 COMPLETED，事件数不变
```

**R-05 的实际影响（比初次判定更严重）**

深查后发现：NestJS 的 `@Post()` 默认返回 **201**，因此以下两个端点此前**实际返回 201**，而文档与预期是 **200**：

| 端点 | 修复前 | 修复后 |
| --- | --- | --- |
| `POST /api/auth/login` | 201 | **200** |
| `POST /api/auth/logout` | 201 | **200** |
| `POST /api/requirements/:id/start` | **201（错误）** | **200** |
| `POST /api/submissions/:id/reviews` | **201（错误）** | **200** |
| `POST /api/requirements` | 201 | 201（显式声明） |
| `POST /api/requirements/:id/submissions` | 201 | 201（显式声明） |

修复方式：所有写端点显式标注 `@HttpCode(...)`，不再依赖框架默认值。

**一次「测试写错了」的记录**

修复过程中新增的一条测试断言「终态下所有角色对所有命令都返回 409」，实跑失败：负责人对 `EDIT` 返回的是 **403**。经核对，**403 才是正确语义** —— 负责人永远不能编辑，角色检查优先于状态检查，此时状态无关紧要。故**修正测试而非改代码**，并在测试中显式写明判定优先级 `404 → 403 → 409`。

> 结论：当测试与代码冲突时，先判断哪个才是对的，不要默认测试一定正确。

## 六、结论

- **自动化质量门禁**：Prettier 格式检查、ESLint 静态检查（0 error / 0 warning）、前后端类型检查与构建、**62 个单元测试**、lockfile 同步校验，全部通过。
- **代码审查修复**：7 项发现（2×P1、3×P2、2×P3）全部修复并回归验证；其中 R-05 深查后发现两个端点状态码确实错误，R-07 是写测试时才暴露的新缺陷。
- **功能正确性**：DEM-01 ~ DEM-08 已由 `scripts/e2e.mjs` 脚本化，一条命令即可产出「期望 / 实际」对照表；DEM-09 / DEM-10 属编排层操作，保留手工步骤。全部用例的预期响应码与消息均已明确标注。
- **幂等语义的边界（走查发现，已修正文档）**：初稿 DEM-07 ① 预期「重复请求回放首次响应」，经走查 `command-pipeline.ts` 确认**对会改变状态的命令不成立** —— 事务外的角色/状态守卫先于幂等占坑执行，重复的 `SUBMIT` 会得到 409 而非回放；幂等的**实质保证（不产生第二条业务记录）仍然成立**。已在 §3 DEM-07 说明原因并改为以「不产生第二条记录」作断言，脚本把状态码差异列为**观察项**而非硬断言。
- **并发与幂等**：幂等占坑与业务变更同事务；乐观锁条件更新保证 `count === 1`；同键异载荷返回 409；缺失 `If-Match` 返回 428。
- **越权防护**：无关账号 404、可见但越权 403、状态不符 409、未登录 401，四类语义明确区分，且优先级固定为 404 → 403 → 409。
- **数据持久化**：业务数据落在命名卷 `da-pgdata`，容器重建后完整保留。

**未覆盖范围（诚实披露）**

- 单元测试覆盖的是**纯逻辑**（状态机、权限、不变量、指纹、前端契约），**不覆盖** HTTP 层与数据库交互。跨容器行为由 `scripts/e2e.mjs` 覆盖 DEM-01~08；DEM-09（故障可重试）与 DEM-10（数据持久化）仍为手工步骤。
- 尚未接入本地 `pre-commit` 钩子与依赖漏洞扫描（`npm audit` / Dependabot）。
- 未做并发压测（多客户端同时提交）；幂等与乐观锁的正确性目前由单测 + 代码审查论证，未做真实并发验证。
- `scripts/e2e.mjs` 已通过语法检查与「服务不可用时优雅退出」验证，但其**首次真实运行**需在 Docker 就绪后完成；脚本期望值取自代码语义，若实测出现偏差将以实测为准并回写本文档。
