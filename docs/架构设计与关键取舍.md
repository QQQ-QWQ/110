# 架构设计与关键取舍

> 本文说明「为什么这样设计」，而不是重复「实现了什么」。功能与接口清单见根目录 `README.md`。

## 一、总体架构

```
┌──────────────────────────────────────────────────────────────────────┐
│                         浏览器（Vue 3 SPA）                           │
│   登录页 │ 需求列表（筛选） │ 需求详情（提交历史 + 事件时间线 + 验收面板）  │
│   会话：httpOnly Cookie（前端不接触 token）                            │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ 同源 /api
┌───────────────────────────────▼──────────────────────────────────────┐
│                       Nginx（web 容器，:80 → :8080）                  │
│   SPA 路由回退  │  静态资源缓存  │  /api 反向代理 → api:3000            │
└───────────────────────────────┬──────────────────────────────────────┘
                                │
┌───────────────────────────────▼──────────────────────────────────────┐
│                        NestJS（api 容器，:3000）                      │
│                                                                      │
│  ┌─────────────────────────── 接入层 ───────────────────────────┐    │
│  │  helmet │ cookie-parser │ ValidationPipe │ AllExceptionsFilter │    │
│  │  AuthGuard（会话解析 → req.currentUser）                       │    │
│  └────────────────────────────┬─────────────────────────────────┘    │
│  ┌────────────────────────────▼──── 领域层（纯函数，无 IO）───────┐    │
│  │  states.ts    四态状态机 · STATE_GUARD · NEXT_STATE · 下一步动作 │    │
│  │  policy.ts    资源级授权：roleOf / assertCanRead / assertCanPerform│   │
│  │  invariants.ts 业务不变量：长度 · URL · 条件 · 退回原因          │    │
│  └────────────────────────────┬─────────────────────────────────┘    │
│  ┌────────────────────────────▼──── 统一写命令管道 ───────────────┐    │
│  │  鉴权 → 状态守卫 → 校验 → 幂等占坑 → 乐观锁 → 业务变更 →        │    │
│  │  事件留痕 → 回填幂等结果（同一事务）                            │    │
│  └────────────────────────────┬─────────────────────────────────┘    │
│  ┌────────────────────────────▼──── 模块层 ──────────────────────┐    │
│  │  auth  │  requirements  │  submissions  │  reviews            │    │
│  └────────────────────────────┬─────────────────────────────────┘    │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ Prisma 6
┌───────────────────────────────▼──────────────────────────────────────┐
│                    PostgreSQL 16（db 容器，命名卷 da-pgdata）         │
│  10 张表 │ CHECK 约束兜底 │ 事务隔离 │ 数据持久化                       │
└──────────────────────────────────────────────────────────────────────┘
```

**分层原则**：领域规则（状态机、权限、不变量）是**纯函数、零 IO**，可以脱离数据库单测；数据库约束只作**兜底**，不作为唯一防线。任何一条规则都能在一个文件里读完、改完、验完。

## 二、十个关键取舍

### 取舍 1：四态硬编码，而非「可配置工作流引擎」

**选择**：状态与流转写死在 `domain/states.ts`，共 4 态 6 命令。

**理由**：题目要求的是**确定性**——「过期/重复操作不改变状态」「已完成为终态」这类断言，只有在状态集合封闭时才可证。引入可配置工作流会带来状态爆炸、权限矩阵需动态求解、测试用例无法穷举三个代价，而收益（小团队场景下几乎不会用到自定义流程）接近于零。

**代价与触发条件**：若未来需要按团队自定义流程，应把 `STATE_GUARD` / `NEXT_STATE` 改为从配置加载，同时保留「终态不可逆」为硬约束。

---

### 取舍 2：权限是资源级四元函数，而非全局 RBAC

**选择**：`Permission = f(User, Requirement, State, Action)`，实现在 `domain/policy.ts`。

**理由**：题目明确要求「每条需求单独判角色：同一用户在其他需求可以是另一角色」。全局 RBAC 只能回答「这个用户是不是负责人」，回答不了「**这条需求上**他是不是负责人」。因此角色必须**从需求行现场推导**（`roleOf`），而不是从用户的全局属性读取。

**落地**：列表查询在 **SQL 层**用 `proposerId = ? OR assigneeId = ?` 过滤，而不是取全量再在内存里筛——既避免越权数据出网，也避免大数据量下的性能塌陷。

> ⚠️ 实现陷阱：`WHERE a OR b AND c` 在 SQL 中因 `AND` 优先级高于 `OR`，会被解析为 `a OR (b AND c)`，导致状态筛选完全失效。本项目用显式括号 / Prisma `AND: [{ OR: [...] }, ...]` 规避，并在代码注释中标注。

---

### 取舍 3：无关账号访问返回 404，而非 403

**选择**：

| 情形 | 响应 |
| --- | --- |
| 需求不存在 **或** 与我无关 | `404 NOT_FOUND` |
| 需求对我可见，但该动作我不被允许 | `403 FORBIDDEN` |
| 需求对我可见、动作允许，但状态不对 | `409 STATE_CONFLICT` |

**理由**：若对无关需求返回 403，攻击者只需遍历 ID 就能枚举出「哪些需求真实存在」，这本身就是信息泄露。对无关资源一律 `404`，把「不存在」和「无权知道存在」合并为同一种响应，**消除枚举信道**。反之，对自己可见的资源，403 是必要反馈——用户需要知道「我看得到它，但我不能改它」。

---

### 取舍 4：幂等「占坑」必须与业务变更在同一事务

**选择**：在业务事务**内**先 `INSERT` 幂等记录（`skipDuplicates`），占坑成功才继续；占坑失败则读取已有记录判断重放。

**理由**：这是本项目最容易写错的地方。若先提交业务、再写幂等记录（两个事务），则两次请求并发时会**双双通过**占坑检查，产生两条业务记录——幂等形同虚设。把占坑与业务放进同一事务，唯一索引 `(userId, operation, idempotencyKey)` 就是并发下的最终仲裁者。

**三种结果**：

| 情形 | 行为 |
| --- | --- |
| 同键 + 同载荷 + 已完成 | 直接回放首次响应体与状态码（`replayed: true`） |
| 同键 + **不同**载荷 | `409 IDEMPOTENCY_CONFLICT`，防止键复用导致串数据 |
| 同键 + 处理中（占坑未回填） | `409`，提示稍后重试 |

**指纹计算**：用 **canonical JSON**（对象键递归排序）序列化请求载荷后取 SHA-256。若直接用 `JSON.stringify`，字段顺序不同会被判为「不同载荷」，误报冲突。

---

### 取舍 5：乐观锁 + 条件更新，而非悲观锁

**选择**：`row_version` 单调递增；写操作必须携带 `If-Match: <rowVersion>`，用 `updateMany({ where: { id, rowVersion }, data: { rowVersion: { increment: 1 } } })` 并校验 `count === 1`。

**理由**：

- 场景是**小团队、低并发**，冲突是偶发而非常态。悲观锁（`SELECT ... FOR UPDATE`）会把「防冲突」的代价平摊到每一次正常操作上，且长事务持锁会放大故障面。
- 乐观锁把冲突检测压缩到一条原子 `UPDATE` 上，零额外锁等待；冲突时返回 `412`，前端提示「数据已被他人更新，请刷新后重试」并自动重载最新版本——这恰好满足题目 DEM-02「A 旧页再次编辑 → 旧页修改失败」与 DEM-07「旧页审核 → 不越级」。

**关键点**：`rowVersion` 的递增必须与业务变更在**同一条 SQL** 中完成（`increment`），否则「读—改—写」之间仍有竞态窗口。

---

### 取舍 6：提交是追加式，V2 不覆盖 V1

**选择**：每次提交 `INSERT` 一条新的 `Submission`（`submissionNo = MAX + 1`），旧记录永不更新或删除。

**理由**：验收的争议往往发生在事后。「负责人说改了、提出者说没改」这类扯皮，只能靠**不可变的版本链**来裁决。覆盖式更新会让历史蒸发，而题目 DEM-06 明确要求「V1/V2 链接和反馈分别保留」。

**连带约束**：

- `Requirement.currentSubmissionId` 指向当前生效的提交；**只有当前提交可被验收**（旧提交验收一律 `409`）。
- 验收时必须**重新逐项勾选**，不允许沿用上一次的勾选结果——否则「V2 自动继承 V1 的通过」会绕过实质复核。
- 验收结果 `checks` 必须**恰好覆盖**全部验收条件：缺项、重复、混入他需求的条件下均 `422`。

---

### 取舍 7：`EVENT.seq = row_version`

**选择**：一次成功的领域命令 = 恰好一个事件，事件的 `seq` 就等于本次操作后需求的 `row_version`。

**理由**：这给「状态推进」和「留痕」建立了一一对应关系，从而获得一个免费且强力的**一致性断言**：`需求事件条数 === row_version`。任何漏记事件、重复记事件、绕过管道直接改状态的行为，都会立刻在这个等式上暴露。

**收益**：历史时间线天然有序（按 `seq` 排序即真实因果顺序），不需要依赖时间戳——而时间戳在并发下可能相同、在时钟漂移下可能倒序。

---

### 取舍 8：统一写命令管道，而非每个 Service 各写一遍

**选择**：所有写操作（创建/编辑/开始/提交/退回/通过）都经过 `pipeline/command-pipeline.ts`，由命令声明**选择性启用**哪些阶段。

**理由**：六条写路径如果各自实现鉴权、状态守卫、幂等、乐观锁、事件留痕，必然出现「某条路径漏了幂等」「某条路径忘了写事件」这类不一致，且修一处漏五处。把横切关注点收敛到一条管道，**新增一个命令时只需声明领域逻辑**，其余全部自动获得。

**代价**：管道接口需要保持足够灵活（并非每个命令都有前置状态、都返回 201）。这是可接受的——灵活性被限制在参数层面，而不是被复制到六个文件里。

---

### 取舍 9：不变量下沉到数据库 CHECK 约束

**选择**：`migration.sql` 手写（Prisma schema 无法表达 CHECK），包含：

- `state IN ('PENDING','IN_PROGRESS','IN_REVIEW','COMPLETED')` —— 状态枚举封闭
- `proposer_id <> assignee_id` —— 负责人不得等于提出者
- 退回记录 `action = 'RETURN'` 时 `reason` 必须非空
- 成果链接 `~* '^https?://[^[:space:]]+$'` —— 格式兜底
- 各类 `UNIQUE`（含幂等键三元组）与查询索引

**理由**：应用层校验会被未来的新入口绕过（脚本、迁移、其他服务）。数据库约束是**最后一道防线**，它保证「即使有人用 psql 直接写，也写不进非法数据」。

**注意**：URL 校验在应用层用**真正的 `new URL()` 解析器**（校验协议与主机名），数据库正则只作兜底——正则永远不可能完整表达 URL 语法。

---

### 取舍 10：文本长度按 Unicode code points 计数

**选择**：`Array.from(value).length`，而非 `value.length`。

**理由**：JavaScript 的 `String.length` 返回 UTF-16 code units。一个 emoji（如 🎉）在 `length` 中算 2，`Array.from` 算 1；中文生僻字在增补平面下同理。用 `length` 做上限校验，会导致「用户看到 200 字，系统说超限」的荒谬结果。中文场景下这不是边缘情况，是常态。

## 三、技术栈选型：为什么是 NestJS 而不是 Java

选型经过**两轮**评审，权重不同，结论发生了翻转。

**第一轮**（响应速度 / 迭代成本 / 安全）→ Java 略胜
JVM 在高并发吞吐与生态成熟度（Spring Security、等保相关组件）上占优。

**第二轮**（维护成本 25% / **交付周期 40%** / 安全 35%）→ NestJS 胜出

| 维度 | 权重 | 结论 |
| --- | --- | --- |
| 维护成本 | 25% | 前后端同语言，团队认知负担低；类型可跨端复用 |
| **交付周期** | **40%** | 无需 JVM 预热与重量级构建；单语言团队上手即产出，**约省 40% 交付时间** |
| 安全 | 35% | 两者均能满足；NestJS 的 Guard/Pipe/Filter 机制与领域分层天然契合 |

**决定性因素**：本项目是**硬性 10 周、无主导语言团队**的一次性交付。在这种约束下，「团队多快能写出正确代码」的权重大于「语言极限性能」。NestJS 与 Vue 同用 TypeScript，一人可端到端改动一条链路，沟通与切换成本接近于零。

**翻转条件**（诚实记录）：若团队已有成熟 Java 班底，或系统需承载高并发（QPS 千级以上）与复杂分布式事务，则应重新评估 Java。

**其余选型**：

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 密码哈希 | bcryptjs | 纯 JS，避免容器内原生模块编译失败（bcrypt 在 slim 镜像上常需 build-essential） |
| 会话存储 | PostgreSQL 表 | 刻意不引入 Redis：减少一个需要运维、需要持久化策略、可能丢数据的组件；会话量级（小团队）远未到需要内存存储 |
| 基础镜像 | `node:22-bookworm-slim` | 不用 alpine：Prisma 在 musl 上需要额外 engine 目标，glibc 更省事 |
| 前端 | Vue 3 + Vite | 构建秒级；产物纯静态，Nginx 托管零运行时 |
| 部署 | 单端口 Nginx 同源反代 | 同源即无 CORS、无跨站 Cookie 问题，安全配置面最小 |

## 四、数据模型要点

```
User ──┬──< Requirement (proposerId)      提出者
       ├──< Requirement (assigneeId)      负责人
       ├──< Session                       会话
       ├──< Submission (submittedById)
       ├──< Review (reviewerId)
       └──< Event (actorId)

Requirement ──┬──< Criterion        验收条件（seq 有序，开始处理后冻结）
              ├──< Submission       提交版本链 V1..Vn（追加式）
              ├──< Event            追加式事件（seq = rowVersion）
              ├──  currentSubmissionId ──▶ Submission   （唯一可被验收的提交）

Submission ──┬──< SubmissionArtifact  成果链接（seq 有序）
             └──< Review              验收记录

Review ──< ReviewCheck   逐项检查结果（criterionId + passed）

IdempotencyRecord  UNIQUE(userId, operation, idempotencyKey)
```

**关键字段**

| 字段 | 作用 |
| --- | --- |
| `Requirement.row_version` | 乐观锁版本号，同时是事件序号来源 |
| `Requirement.current_submission_id` | 唯一可验收的提交；旧提交验收被拒 |
| `Requirement.state` | 四态，受 CHECK 约束封闭 |
| `Event.seq` | 等于操作后的 `row_version`，保证一命令一事件 |
| `ReviewCheck.criterion_id` | 把验收结果锚定到具体条件，可逐项追溯 |
| `IdempotencyRecord.request_hash` | canonical JSON 指纹，防止幂等键复用串数据 |

## 五、部署拓扑与数据持久化

- **三容器**：`db`（PostgreSQL 16）、`api`（NestJS）、`web`（Nginx + 静态产物）。
- **启动顺序**：`db` 通过 `pg_isready` 健康检查 → `api` 启动 → `entrypoint` 循环重试 `prisma migrate deploy` → 执行幂等 seed → 启动应用；`web` 依赖 `api`。
- **数据持久化**：业务数据全部落在命名卷 `da-pgdata`。`docker compose down && docker compose up` 后数据完整保留（DEM-10）。
- **幂等启动**：seed 使用**固定 UUID + upsert**，重复启动不会产生重复数据，也不会覆盖已有业务进展——这一点很重要，否则「重启容器」会毁掉评审过程。

## 六、已知边界与演进路径

| 边界 | 现状 | 演进方向 |
| --- | --- | --- |
| 单实例会话 | 会话存 PG，单实例 | 水平扩展需共享会话或粘性会话 |
| 无 HTTPS | 内网 http，`COOKIE_SECURE=false` | 生产启用 TLS 并置为 `true` |
| 无审计导出 | 事件表留痕，未提供导出接口 | 增加审计导出与哈希链防篡改 |
| 无通知 | 状态变化不推送 | 接入站内信 / 邮件 |
| 未做等保加固 | 超出本次考核范围 | 见内部规划文档的等保 2.0 控制项映射 |
