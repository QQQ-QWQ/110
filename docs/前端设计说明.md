# 前端设计说明

> 适用版本：`frontend/`（Vue 3 + TypeScript + Vite）
> 对应后端：NestJS + Prisma + PostgreSQL，接口契约见根 `README.md` §5。
> 本文回答四件事：**有哪些模块、页面长什么样、流程怎么走、为什么这样实现**。

---

## 一、一页速览

| 维度 | 结论 |
| --- | --- |
| 技术栈 | Vue 3.5（Composition API + `<script setup>`）、TypeScript strict、Vue Router 4、Vite 6 |
| 依赖策略 | **运行时零 UI 框架**，只依赖 `vue` + `vue-router`；组件全部自研，避免引入整套设计系统带来的体积与升级风险 |
| 样式方案 | 原生 CSS + 设计令牌（CSS 变量），四层文件：`tokens → base → components → responsive` |
| 响应式 | 三档断点：mobile `<640px` / tablet `640–1023px` / desktop `≥1024px`，**桌面优先编写、向下降级** |
| 状态管理 | 不引入 Pinia：跨页面共享的只有「当前用户」与「全局提示」，用模块级 `ref` + 组合式函数即可，减少一层抽象 |
| 组件规模 | 15 个可复用组件、5 个组合式函数、2 个工具模块 |
| 质量门禁 | Prettier ✅ / ESLint 0 error ✅ / `vue-tsc` 0 error ✅ / **75 个单测** ✅ / `vite build` ✅ |

## 二、功能模块划分

前端按「**外壳 / 页面 / 业务组件 / 基础组件 / 能力层**」五层组织，依赖只能自上而下，禁止反向引用。

```
┌─────────────────────────────────────────────────────────┐
│ 外壳 App.vue        登录态 · 顶栏 · 全局提示宿主 · 跳转锚点 │
├─────────────────────────────────────────────────────────┤
│ 页面 views/         登录 · 列表 · 详情（路由级懒加载）      │
├─────────────────────────────────────────────────────────┤
│ 业务组件 components/ 引导 · 条件 · 提交卡 · 时间线 · 验收面板│
├─────────────────────────────────────────────────────────┤
│ 基础组件 components/ 按钮 · 弹窗 · 徽标 · 提示 · 空态 · 骨架 │
├─────────────────────────────────────────────────────────┤
│ 能力层              api.ts · composables/ · utils/ · types │
└─────────────────────────────────────────────────────────┘
```

**五个功能模块**（对应题目要求的能力面）：

| 模块 | 载体 | 职责 |
| --- | --- | --- |
| 会话与身份 | `App.vue`、`router.ts`、`useCurrentUser` | 登录态缓存、路由守卫、顶栏身份展示、登出 |
| 需求列表与筛选 | `ListView.vue` | 范围（全部/我提出的/我负责的）+ 状态 + 关键词三条件组合筛选，列表内快捷「开始处理」 |
| 需求详情与流转 | `DetailView.vue`、`NextStepCard` | 元信息、正文、验收条件、动作区、下一步引导 |
| 提交与验收 | `SubmissionCard`、`ReviewPanel` | V1/V2 独立留痕、逐项勾选、退回原因必填、全通过才可完成 |
| 留痕与反馈 | `EventTimeline`、`ToastHost`、`SkeletonList`、`EmptyState` | 操作时间线、加载/空/成功/失败四态反馈 |

## 三、页面结构

### 3.1 路由表

| 路径 | 名称 | 组件 | 守卫 |
| --- | --- | --- | --- |
| `/login` | `login` | `LoginView` | 公开；已登录则重定向到列表 |
| `/` | `list` | `ListView` | 需登录 |
| `/requirements/:id` | `detail` | `DetailView` | 需登录（可见性由后端 404 判定） |
| `/:pathMatch(.*)*` | — | 重定向到 `/` | — |

三个视图均为**路由级动态导入**，首屏只加载登录/列表所需代码。

四态反馈：

| 状态 | 呈现 |
| --- | --- |
| 加载中 | `SkeletonList` 骨架屏（保持布局形状，避免内容到达时跳动） |
| 空结果 | `EmptyState` —— 区分「筛选后为空」与「本来就没有」，并给出「重置筛选 / 新建第一条需求」出口 |
| 加载失败 | 内联 `AlertBox` + 就地「重试」按钮 |
| 操作结果 | 顶部 `Toast`（成功自动消失；**失败常驻**直到用户关闭） |

## 四、核心交互流程

### 4.1 主流程（与后端四态状态机严格对齐）

```
提出者创建 ──▶ 待处理 PENDING ──负责人「开始处理」──▶ 进行中 IN_PROGRESS
                   │                                      │
                   │ 仅此阶段可编辑正文与验收条件            │ 负责人提交成果 Vn
                   ▼                                      ▼
               （冻结后不可改）                        待验收 IN_REVIEW
                                                          │
                             提出者逐项验收 ───────────────┤
                                │                         │
                    有未通过项 → 退回（原因必填）      全部通过 → 确认完成
                                │                         │
                                ▼                         ▼
                          回到进行中                 已完成 COMPLETED（终态）
```

### 4.2 关键交互设计

| 场景 | 设计 | 为什么 |
| --- | --- | --- |
| **动作可见性** | 动作按钮**只由后端返回的 `nextActions` 驱动渲染**，前端不自行推断 | 权限是 `f(用户, 需求, 状态)` 四元函数，前端复制一份判定逻辑必然与后端漂移 |
| **下一步引导** | `NextStepCard` 把 `state + myRole + nextActions` 翻译成人话，分 `action / wait / done` 三种语气 | 对应验收项「提出者和负责人均能看懂下一步该做什么」；`wait` 语气明确说明在等谁，避免误以为页面卡住 |
| **防重复提交** | 提交中按钮 `loading` 且禁用；同时 `api.ts` 为每个写请求生成 `Idempotency-Key` | 双击、网络重试都不会产生第二条业务记录（后端同键同载荷直接回放） |
| **旧页面操作** | 写请求强制带 `If-Match: rowVersion`；收到 412/409 时**自动重新加载**并提示「已为你刷新到最新数据」 | 旧页面在状态已变化后操作必须失败且给明确提示 |
| **失败保留输入** | 校验失败或服务端拒绝时**不清空表单**，错误就近展示在对应字段下 | 考核硬要求：失败时保留用户尚未提交的当前输入并允许重试 |
| **验收防漏项** | 打开验收面板时全部重置为「未通过」；存在未通过项则「确认完成」按钮禁用 | 防止复用上一次勾选结果造成误验收；前端先拦一道，后端仍会校验 |
| **角色视角** | `RoleTag` 跟着**每条需求**渲染，而不是放在顶栏 | 同一个人在不同需求中可能分别是提出者与负责人 |
| **可见性拒绝** | 无关账号访问详情 → 后端返回 404；页面提示「需求不存在或你无权访问」，并说明「不会暴露该需求是否存在」 | 避免通过状态码枚举出需求是否存在 |

### 4.3 验收面板（最复杂的一条链路）

```
点击「逐项验收」
   │
   ├─ 打开即重置：全部条件 = 未通过，原因 = 空，错误 = 空
   │
   ├─ 勾选条件 ──▶ 进度条实时更新「已通过 2 / 3」
   │
   ├─ 点「确认完成」
   │     └─ 未全部通过？ → 按钮本就禁用 + 提示「存在未通过的验收条件」
   │
   └─ 点「退回修改」
         ├─ 原因为空？ → 就地提示「退回时必须填写具体修改原因」，**保留已勾选结果与原因**
         └─ 通过 → 提交 { action, reason, checks[] }
               ├─ 成功 → 关闭面板 + Toast + 重新拉取详情（时间线与提交卡同步更新）
               └─ 失败 → **面板保持打开**，展示服务端文案，勾选与原因原样保留
```

## 五、响应式设计

### 5.1 断点与策略

| 断点 | 宽度 | 主要变化 |
| --- | --- | --- |
| desktop | `≥1024px` | 基准态：工具条一行铺开，搜索框自适应拉伸，列表横向排列 |
| tablet | `640–1023px` | 页面留白收窄，工具条允许换行，元信息栅格自动降到 `150px` 最小列宽 |
| mobile | `<640px` | 工具条纵向堆叠；筛选折叠为「筛选 · N」按钮；列表项转纵向卡片；弹窗变全屏抽屉；触控目标放大到 ≥44px |
| 超小屏 | `<380px` | 顶栏隐藏品牌文字（只留标记），元信息降为单列 |

### 5.2 关键适配点

- **弹窗 → 全屏抽屉**：移动端 `.overlay` 取消内边距、`.modal` 撑满 `100dvh`、圆角归零；底部操作区固定并预留 `env(safe-area-inset-bottom)`，避免被 iOS 手势条遮挡。调用方无需任何感知——`BaseModal` 用法在两端完全一致。
- **触控目标**：移动端 `.btn` 高度提升到 44px（`--tap-min`），验收项复选框放大到 20px。
- **筛选折叠**：由 `useBreakpoint` 判断，移动端默认折叠并显示生效条件数量；桌面端恒展开。这是**唯一**需要在 JS 侧感知断点的场景——其余全部交给 CSS。
- **单位选择**：视口高度用 `dvh` 而非 `vh`，规避移动浏览器地址栏收缩导致的跳动。
- **列表项**：移动端由 `flex-row` 转 `flex-column`，动作按钮整行等宽铺开，避免窄屏按钮换行错位。

### 5.3 可访问性

| 项 | 实现 |
| --- | --- |
| 键盘可达 | 全部交互元素为原生 `button` / `input` / `select` / `textarea`；`:focus-visible` 统一焦点环 |
| 跳转锚点 | 每页首部提供「跳到主要内容」，`<main id="main-content">` |
| 弹窗 | `role="dialog"` + `aria-modal`；焦点陷阱（Tab 循环）、Esc 关闭、关闭后焦点归还触发元素 |
| 滚动锁 | `body.is-locked`，**引用计数**实现，支持弹窗叠加时先关后开不误解锁 |
| 读屏播报 | 错误 `role="alert"`（立即打断），普通提示 `role="status"`（礼貌播报）；骨架屏对读屏隐藏，只播报一句「加载中」 |
| 动效降级 | `prefers-reduced-motion: reduce` 时全局关闭动画与过渡 |

## 六、工程结构与可维护性约定

### 6.1 目录结构

```
frontend/src/
├── main.ts                     应用入口
├── App.vue                     外壳：登录态 / 顶栏 / Toast 宿主 / 跳转锚点
├── router.ts                   路由与登录守卫
├── api.ts                      统一 HTTP 客户端（If-Match / Idempotency-Key 契约）
├── types.ts                    与后端一一对应的类型 + 文案映射
├── styles/
│   ├── index.css               样式入口（唯一被 main.ts 引用）
│   ├── tokens.css              设计令牌：颜色/间距/圆角/阴影/层级/尺寸
│   ├── base.css                重置、排版、焦点、跳转锚点、动效降级
│   ├── components.css          组件样式（桌面态）
│   └── responsive.css          断点覆盖（必须最后加载）
├── composables/
│   ├── useToast.ts             全局提示（单例 store）
│   ├── useAsyncAction.ts       异步动作统一封装（busy / error / lastError）
│   ├── useCurrentUser.ts       当前用户缓存（顶栏 + 列表页共用）
│   ├── useBodyScrollLock.ts    弹窗滚动锁（引用计数）
│   ├── useFocusTrap.ts         焦点陷阱 + Esc + 焦点归还

├── components/                 15 个可复用组件
└── utils/
    ├── format.ts               日期/相对时间/首字/截断
    └── validate.ts             输入校验（与后端 invariants 一一对应）
```

### 6.2 组件复用矩阵

| 组件 | 登录页 | 列表页 | 详情页 | 说明 |
| --- | :-: | :-: | :-: | --- |
| `BaseButton` | ✅ | ✅ | ✅ | 变体 + 尺寸 + loading + block |
| `BaseModal` | | ✅ | ✅ | Teleport + 焦点陷阱 + Esc + 滚动锁 |

| `EmptyState` | | ✅ | ✅ | 空态解释 + 出口 |
| `SkeletonList` | | ✅ | ✅ | 加载骨架 |
| `ToastHost` | ✅（全局） | ✅ | ✅ | 挂在外壳，跨页面存活 |
| `AppTopBar` | | ✅ | ✅ | 外壳级 |
| `StatusBadge` | | ✅ | ✅ | 四态徽标 |
| `RoleTag` | | ✅ | ✅ | 按需求判定的角色 |
| `NextStepCard` | | | ✅ | 下一步引导 |
| `CriteriaList` | | | ✅ | 详情只读 / 提交卡带 ✓✗ 两用 |
| `SubmissionCard` | | | ✅ | Vn 独立留痕 |
| `EventTimeline` | | | ✅ | 操作时间线 |
| `ReviewPanel` | | | ✅ | 验收链路整体封装 |

> `CriteriaList` 是「同一组件、两种形态」的典型：详情页不传 `checks` 时是只读清单，提交记录里传 `checks` 时自动补上 ✓/✗，避免维护两套几乎相同的列表。

### 6.3 五条可维护性约定

1. **单一落点**：颜色/间距只在 `tokens.css`；状态文案只在 `types.ts`；校验规则只在 `utils/validate.ts`；HTTP 契约只在 `api.ts`。改一处即全局生效。
2. **令牌化**：组件样式**不写魔法值**，一律引用 CSS 变量。未来换肤（深色模式）只需改 `tokens.css`。
3. **双端校验同口径**：`utils/validate.ts` 的常量与规则逐条对应后端 `domain/invariants.ts`；长度一律按 **Unicode code points** 计数（`Array.from`），并显式拒绝含空白字符的 URL——与数据库 `CHECK` 判定一致，避免「前端放行、后端 500」。
4. **依赖单向**：`views → components → composables/utils → api/types`，禁止反向引用；基础组件不感知任何业务概念（`BaseModal` 不知道什么叫「需求」）。
5. **反馈四态全覆盖**：任何数据区域都必须明确处理「加载中 / 空 / 成功 / 失败」，不允许出现空白页面或静默失败。

## 八、已知限制

- **未接入交互级组件测试**：现有组件测试为 SSR 渲染断言（不执行 `onMounted`、不模拟点击），因此「数据加载」「点击后状态变化」由 `scripts/e2e.mjs` 的端到端流程与手工验收覆盖。若需补齐，可引入 `jsdom` + `@vue/test-utils`，代价是新增两个 devDependency。
- **两个组合式函数已做 SSR 防护**：`useFocusTrap` / `useBodyScrollLock` 在无 `document` 环境下自动跳过 DOM 操作，因此可在非浏览器环境安全渲染。
- **无深色模式**：设计令牌已按换肤要求分层，但当前只提供浅色一套；接入深色只需在 `tokens.css` 增加一份 `@media (prefers-color-scheme: dark)` 覆盖。
- **无国际化**：文案为简体中文硬编码，集中在模板与 `types.ts` 的映射表中；如需多语言需引入 `vue-i18n`。
- **列表未做虚拟滚动**：当前按「仅显示与本人相关」的规模设计（小团队），数百条量级无性能问题；若需求数量级增长需引入虚拟列表。
- **断点仅 JS 侧使用一处**：`useBreakpoint` 只服务于移动端筛选折叠，其余适配全部由 CSS 承担——这是刻意的，避免 JS 与 CSS 两套断点判断产生分歧。
