### 本次端到端实跑所用的环境（与上表的差异，必须说明）

本文 §4.2 的端到端结果**不是**在 `docker compose` 栈上取得的。原因是执行时
**Docker Desktop 引擎无法启动**：`com.docker.service` 处于 Stopped，而当前会话
不具备管理员权限（`IsAdmin=False`），无法启动该服务（`Start-Service` 返回
「无法打开计算机上的 com.docker.service 服务」）；`sc.exe` 与 `wsl.exe` 又被本机
安全策略拦截，无法绕行。启动 Docker Desktop 主程序后其 `com.docker.backend.exe`
在 10 秒内自行退出（`%LOCALAPPDATA%\Docker\log\host\Docker Desktop.exe.log` 可见
`backend process exited`），引擎始终未就绪。

因此改用**等价替换**取得真实端到端证据：

| 组件 | Compose 路径 | 本次实跑路径 |
| --- | --- | --- |
| 数据库 | `postgres:16-alpine` 容器 | **PostgreSQL 16.9**（官方 Windows 便携版，独立数据目录，端口 5433） |
| 后端 | `api` 容器（Dockerfile 多阶段构建） | 同一份 `dist/`（`npm run build` 产物），`node dist/main.js` 直接运行，端口 3100 |
| 前端 | `web` 容器（nginx 静态托管 + `/api` 反代） | **未参与**（§4.2 全部为 HTTP 接口层验证，不依赖前端） |
| 迁移与种子 | `docker-entrypoint.sh` 内 `prisma migrate deploy` + `node dist/seed.js` | 手工执行**完全相同的两条命令** |

**差异的影响范围**：被测对象（NestJS 应用、Prisma 迁移、领域不变量、HTTP 语义）
完全一致；仅「数据库是宿主机进程而非容器」「未经过 nginx 反代」两点不同。
因此 §4.2 可以证明**应用与数据库的行为**，但不能替代对
「`docker compose up --build` 一条命令跑通三容器」这一交付要求的验证 ——
该项仍待 Docker 引擎可用后补做（见 §7 遗留项）。

> 这次绕行并非纯粹的替代方案：它**直接暴露了两个此前从未被发现的缺陷**
> （见 §4.4），两者都会让 `docker compose up --build` 实际不可用。

### DEM-07 重复 / 过期 / 终态操作

> **⚠️ 本节预期已按代码语义修正，并经实跑确认。** 初稿把「同一 `Idempotency-Key` 重复提交」的预期写成
> 「两次响应完全一致（回放首次结果）」。走查 `command-pipeline.ts` 并**实跑验证**后确认该预期**不成立**：
> 事务外的守卫（可见性 404 → 角色 403 → **版本 412** → 状态 409）与幂等占坑之前，
> 首次 `SUBMIT` 成功已使 `row_version` 递增，因此重复请求携带的 `If-Match` **立即过期**，
> 会被**版本守卫以 412 挡下**，根本走不到「回放已落库响应」那一步。
>
> 结论：**回放路径对「执行后会改变状态的命令」不可达**，只对 `CREATE`（无状态/版本守卫）
> 以及「执行后状态与版本均仍允许该动作」的场景（如 `PENDING` 下的 `EDIT` 且版本未变）可达。
> 但幂等的**实质保证仍然成立**——重复请求绝不会产生第二条业务记录。
> 故本节改为以「不产生第二条业务记录」作为断言，并在脚本中把状态码差异列为**观察项**。

```bash
# ① 幂等：同一 Idempotency-Key 重复请求 → 只产生一次业务记录
#    用 CREATE 验证回放路径（CREATE 无状态与版本守卫，回放可达）
curl -s -b $JA -X POST http://localhost:8080/api/requirements \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: dem07-idem' \
  -d '{"title":"幂等验证","description":"验证同键只创建一次","assigneeId":"00000000-0000-4000-8000-000000000002","criteria":["条件一"]}' > /tmp/r1.json
curl -s -b $JA -X POST http://localhost:8080/api/requirements \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: dem07-idem' \
  -d '{"title":"幂等验证","description":"验证同键只创建一次","assigneeId":"00000000-0000-4000-8000-000000000002","criteria":["条件一"]}' > /tmp/r2.json
diff /tmp/r1.json /tmp/r2.json && echo '两次响应完全一致（回放首次结果）'
# 预期：两次均 201，响应体完全相同（同一个 id），数据库中只新增 1 条需求

# ② 同键不同载荷 → 409
curl -s -b $JA -X POST http://localhost:8080/api/requirements \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: dem07-idem' \
  -d '{"title":"幂等验证（载荷不同）","description":"验证同键只创建一次","assigneeId":"00000000-0000-4000-8000-000000000002","criteria":["条件一"]}'
# 预期：409（IDEMPOTENCY_KEY_REUSED）

# ③ 重复提交（状态已改变）→ 被守卫拒绝，但不得产生第二条记录
curl -s -b $JB -o /dev/null -w '%{http_code}\n' -X POST http://localhost:8080/api/requirements/$RID7/submissions \
  -H 'Content-Type: application/json' -H "If-Match: $V" -H 'Idempotency-Key: dem07-dup' \
  -d '{"artifacts":["https://example.com/dup"],"note":"重复请求测试"}'
# 第一次：201
# 第二次（同键同载荷同版本）：409（状态守卫先于幂等占坑）
curl -s -b $JA http://localhost:8080/api/requirements/$RID7/history | grep -c '"submissionNo"'
# 预期：1（重复请求未产生第二条提交记录）—— 这才是幂等的实质保证

# ④ 终态后再次退回 → 不改变状态、不产生虚假历史
curl -s -b $J -o /dev/null -w '%{http_code}\n' -X POST http://localhost:8080/api/submissions/$SID2/reviews \
  -H 'Content-Type: application/json' -H 'If-Match: 7' -H 'Idempotency-Key: dem07-final' \
  -d "{\"action\":\"RETURN\",\"reason\":\"终态后退回\",\"checks\":[{\"criterionId\":\"$C1\",\"passed\":false},{\"criterionId\":\"$C2\",\"passed\":false},{\"criterionId\":\"$C3\",\"passed\":false}]}"
# 预期：409，状态仍为 COMPLETED，事件数不变
```

### 4.4 端到端实跑发现的两个缺陷（本轮修复）

这两个缺陷此前**从未被发现**，因为端到端脚本从未真正跑过（Docker 引擎不可用）。
它们的共同特征是：单元测试与静态检查全绿、代码审查也没看出来 ——
只有把服务真正跑起来才会暴露。

#### 缺陷 1（P0）：种子数据的循环外键写序错误，会让容器直接起不来

**现象**：`node dist/seed.js` 报 `P2003`，退出码 1，第 3 条需求（待验收）写入失败。

```
PrismaClientKnownRequestError:
  code: 'P2003',
  meta: { modelName: 'Requirement', constraint: 'requirement_current_submission_id_fkey' }
```

**根因**：`requirement.current_submission_id` 与 `submission.requirement_id` **互为外键**：

```
requirement.current_submission_id ──▶ submission.id
submission.requirement_id         ──▶ requirement.id
```

`seed.ts` 在第 178 行创建需求 3 时就带上了 `currentSubmissionId: S.reviewV1`，
而那条提交在第 206 行才创建 —— 任何单条 INSERT 都无法同时满足这个环。

**为什么是现在才炸**：迁移 `0002_current_submission_fk`（commit `5d5a11a` 的
R-02 修复）给这个指针**补加了外键**。在此之前它是裸列，写序颠倒也不报错。
也就是说：**修 R-02 引入了新缺陷，而由于 CI 的 `migrations` job 只校验约束存在、
不校验种子能否写入，这个回归一路漏到了端到端实跑。**

**放大效应（比种子失败本身更严重）**：`docker-entrypoint.sh` 开头是 `set -e`，
而 `node dist/seed.js` 在失败时 `process.exitCode = 1`。于是
**容器启动脚本会中止 → `api` 容器起不来 → `docker compose up --build` 交付要求直接失败**。

**修复**（`backend/src/seed.ts`）：拆成三步，显式打破环

```
① 建需求（currentSubmissionId 留空）
② 建提交与成果链接（此时需求已存在，submission.requirement_id 可满足）
③ 回填 requirement.currentSubmissionId（此时提交已存在，外键可满足）
```

**验证**：重置数据库后完整重跑，`seed` 退出码 0，数据为
`3 users / 3 reqs / 7 criteria / 1 subs / 6 events`；再跑一次条数不变（幂等）。

#### 缺陷 2（P1）：版本过期被误报成状态冲突（412 被 409 抢先）

**现象**：`DEM-02 ★ 旧版本号提交 → 412` 实测返回 **409**。

**根因**：`command-pipeline.ts` 的事务外预检与事务内复检都把
`assertCanPerform`（内部先判角色 403、再判状态 409）排在版本校验之前：

```ts
assertCanPerform(actorId, pre, pre.state, command);   // ← 状态守卫在这里抛出 409
if (pre.rowVersion !== expectedRowVersion) throw Errors.stale();  // ← 永远走不到
```

**为什么 412 才是对的**：

1. **HTTP 语义**：`If-Match` 是请求前置条件，RFC 9110 §13.1.1 要求它**先于**方法处理求值。
2. **可操作性**：客户端屏幕上还是旧状态，收到 409「当前状态不允许该操作」只会困惑；
   收到 412「数据已被他人更新，请刷新后重试」才知道该做什么。

`docs/测试与验证记录.md` §3 DEM-02 与 `scripts/e2e.mjs` 都写的是 412 ——
**只有实现不一致**，所以是实现的问题。

**修复**（`policy.ts` + `command-pipeline.ts`）：把角色与状态判定拆成两段，
让版本校验插在中间，形成明确的四级顺序：

```
可见性 404  →  角色 403  →  版本 412  →  状态 409
```

> 为什么可见性必须仍在最前：否则对**他人**资源发一个过期版本号，
> 就能通过 412 与 409 的差异把「这条需求存在」试出来 —— 那是个枚举漏洞。
> 这条约束已在新增单测中显式断言。

**附带的一致性收益**：`assertCanPerform` 保持原行为不变（角色 → 状态），
所以既有的 10 条权限单测**一条都没改**；新增 3 条单测覆盖拆分后的两段行为
与四级顺序（含「不可见账号即使版本也过期仍必须 404」的负例）。

**验证**：后端单测 47 → **50** 全通过（当轮用例数，现为 76）；端到端重跑 **44/44 通过、退出码 0**（当轮断言数，脚本现为 56 项）。

#### 小结：这两个缺陷说明什么

| 检查层 | 为什么没拦住 |
| --- | --- |
| 单元测试（当时 50 个） | 覆盖的是纯逻辑（状态机/权限/不变量/指纹），**不碰数据库与 HTTP 层** |
| ESLint / Prettier / `tsc` | 语法与风格正确，写序错误与判定顺序都不是「错误」 |
| CI `migrations` job | 只校验「迁移能在空库跑通」「约束存在」，**不校验种子能否写入** |
| CI 后端 job | 只跑 `build` + 单测，**不起服务** |
| 人工代码审查 | 两处都是「看起来合理」的代码；缺陷 1 是跨文件的时序问题，缺陷 2 是错误优先级问题 |

**结论：端到端实跑不可被任何静态检查替代。** 这也直接说明 CI 应当增加
「启动服务并跑一遍 e2e」的 job（见 `docs/后端架构审核与CI排查报告.md` §5.3）。

> **后续（2026-10-05 同日完成）**：该 job 已落地并验证 —— `.github/workflows/ci.yml`
> 新增 `e2e` job（postgres service + `prisma generate` / `migrate deploy` / `build` /
> `seed` / 种子完整性断言 / 起 API / 跑本文件 §4.2 的脚本）。
> 远端 CI run #8（commit `610dfa7`）**6/6 job 全绿**，新增 job 约 37 秒。
> 也就是说：上表「为什么没拦住」中，**第 3、4 两行已经不再是缺口** ——
> 缺陷 ① 会在 seed 步骤（`P2003`，退出码 1）或紧随其后的种子完整性断言处变红，
> 缺陷 ② 会在 e2e 脚本的 DEM-02 处变红（期望 412、实际 409）。

### 7.1 E1 分页：为什么单测要「模拟翻页」

分页最容易出的错不是「少一页」，而是**翻页时重复或漏行**：只按 `createdAt` 排序时，同一毫秒创建的多行顺序不稳定；决胜键方向写反（`id < cursor.id` 写成 `>`）则第二页起直接错位。这两种错误在数据量小时完全看不出来。

因此 `test/pagination.test.js` 构造了 **25 行、每 5 行共用同一毫秒**的数据集，用与 `requirements.service.ts` 中 `if (cursor)` 分支**逐字对应**的条件模拟翻页，断言：逐页取完不重复、不遗漏、顺序与全量排序一致。另有一条**反向验证**——「若决胜键方向写反，该样本会立刻暴露」，用来证明测试本身有效，而不是恰好通过。

### 7.2 S1 清理：两层验证各管什么

- **单测（14 条）**用 stub 验证「过滤条件写对了」，其中包含一张 **where 子句 vs 判定函数的一致性矩阵**：这类不一致没有任何编译期提示，完全可能单测通过而线上删错。
- **`scripts/verify-retention.mjs`** 对真实 PostgreSQL 插入 5 类样本行（过期 / 未过期会话、超期 / 未超期 `COMPLETED` 记录、**超 100 小时仍在 `PROCESSING` 的记录**），跑一次清理后断言删留边界，**5/5 通过**，并自行清理测试行以便重复执行。

最关键的一条断言是「**`PROCESSING` 超 100h 必须保留**」—— 删掉它会让同一幂等键被重新占坑，从而允许同一请求被重复执行业务写入，幂等语义直接失效。

### 7.3 E3：一处必须标明的未验证项

`container_name` 的移除由 `docker-compose config` 确认（配置可解析、三处均已消失）。但 **nginx 的改动无法在本环境执行**：既没有可用的 Docker 引擎，也没有 nginx 二进制。只做了配置结构解析（`nginx-conf` 解析成功，`resolver` / `set` / `proxy_pass` 等指令均被正确识别）—— 这能证明**语法结构**没问题，**不能证明语义**（例如变量式 `proxy_pass` 与 `$request_uri` 拼接后的实际转发行为）。

若将来 `docker compose up` 后 `/api/` 返回 502，应优先检查此处。

## 八、P1 首项（C4 本地前置检查）的落地验证（2026-10-05）

对应《后端架构审核与CI排查报告》§5.3 的 C4。目标：把反馈周期从「推送 → 等 3~5 分钟」
压到 **1 秒**，并消除「本地过了 CI 不过」这类最难排查的偏差。

### 8.1 设计：本地与 CI 共用同一份实现

`scripts/preflight.mjs` 不只是给开发者用的便利脚本 —— CI 的 `hygiene` job **直接调用它**
（`node scripts/preflight.mjs --mechanical`）。于是「本地 preflight 绿」与「CI hygiene 绿」
是**同一件事**，而不是两套会各自漂移的检查。

代价是这些检查在 CI 里合并成了一个步骤，粒度不如从前（原来 4 个独立步骤）。之所以接受，
正是因为**本环境读不到 CI 的 job 日志**：合并后失败时本地跑一遍就能看到是哪个检查、哪个文件。

### 8.2 检查项（8 项，分两层）

| 层 | 检查项 | 依赖 |
| --- | --- | --- |
| 机械层 | 行尾（索引 + 关键文件必须 LF）、密钥文件未入库、构建产物未入库、lockfile 与 `package.json` 同步 | 无（纯 git + fs） |
| 工具层 | Prisma schema 已格式化、后端 Prettier、前端 Prettier | 需先 `npm ci` |

工具层缺依赖时**明确报错**而非静默跳过 —— 静默跳过会让人误以为「检查过了」，那比没有检查更危险。

### 8.3 负例验证：这些检查真的会「咬人」

一条从不报红的检查等于没有检查。因此逐项制造真实违规（完整矩阵亦见报告 §7.1）：

| # | 检查项 | 制造的违规 | 结果 |
| --- | --- | --- | --- |
| 1 | 行尾 | `backend/docker-entrypoint.sh` 写成 CRLF | ✅ 退出码 1，只有该项报红 |
| 2 | 密钥未入库 | `git add -f .env.production` | ✅ 退出码 1，只有该项报红 |
| 3 | 构建产物未入库 | `git add -f backend/dist/_probe.js` | ✅ 退出码 1，只有该项报红 |
| 4 | lockfile 同步 | 往 `backend/package.json` 加未安装的依赖 | ✅ 退出码 1，只有该项报红 |
| 5 | Prisma schema 格式 | 把 `id` 行缩进 2→4 空格**并入库** | ✅ 退出码 1，只有该项报红 |
| 6 | Prettier | 往 `main.ts` 追加一行未格式化代码 | ✅ 退出码 1，只有该项报红 |

每项测试后都还原现场并复跑，确认回到全绿（退出码 0）。清理后工作区只剩本次的预期改动。

**第 5 项的陷阱**：实现是「先 `prisma format`，再 `git diff --quiet`」。只把文件改坏、
**不入库**是不会报红的 —— 因为 format 会把工作区改回与 HEAD 一致，此时确实没有问题。
必须模拟「有人把未格式化的 schema 提交了」（改动已进索引）才会报红。自测时极易误判为「检查失灵」。

### 8.4 一处必须说明的局限

本机 `core.autocrlf=true` 会在 `git add` 时把 CRLF 规范化成 LF，因此「**索引里存在 CRLF**」
这一状态在本机几乎无法复现。第 1 项实际测的是「关键文件在**工作区**是 CRLF」——
它对应一个真实故障：**`docker build` 的构建上下文取自工作区，而不是 git 索引**，
一个 CRLF 的入口脚本会被原样打进镜像并报 `$'\r': command not found`，
而此刻 `git status` 可能是干净的（索引已是 LF）。

索引层的 CRLF 只在 CI（`autocrlf=false`）或 `.gitattributes` 被人改坏时才出现 ——
所以这一条同时也是「**有人删掉 `* text=auto eol=lf`**」的回归守卫。

### 8.5 顺带修掉的一处本地噪音

3 个文档（`代码审查标准与流程.md` / `后端架构审核与CI排查报告.md` / `测试与验证记录.md`）
在工作区是 CRLF（索引是 LF，因此**提交内容是正确的**）。这本身无害，但会让每次 `git add`
打印 `CRLF will be replaced by LF` 的警告，并让基于 `grep '\r'` 的检查产生**假阳性**（本次就误报过一次）。

已用 `node scripts/preflight.mjs --fix` 就地规范化为 LF；随后 `git add` 确认**无内容变更**
（逐字节与 HEAD 的 blob 比对一致）。

## 九、P1 第二项（S5 请求编号贯穿日志）的落地验证（2026-10-05）

对应《后端架构审核与CI排查报告》§5.2 的 S5。

### 9.1 要解决的场景与设计取舍

场景：用户报「刚才点了一下就报错了」，服务端日志里却只能靠时间去猜是哪一条请求。

采用**轻量版**：中间件 + 异常过滤器 + 访问日志。刻意**不**引入 AsyncLocalStorage / nestjs-cls ——
那需要改动所有 service 的签名（或在每个入口包一层），而本项目并没有跨多层异步的日志关联需求：
异常过滤器已经同时拿得到 `request` 与 `response`。

三条取舍：

1. **透传但校验**。客户端/网关传来的编号会被沿用（跨层才能串起来），但只接受**安全形态**：
   可见 ASCII 标识符子集、长度 ≤ 128。理由是这个值会被写进日志行与响应头 —— 不加限制就等于
   开放了「用换行符伪造日志条目」与「超长串撑爆日志」两个口子。
2. **响应头始终回传**，不只是 5xx。前端/运维在任何一次请求上都能拿到编号，排查时不必先复现错误。
3. **只有 5xx 的响应体带编号**。4xx 是调用方自己的问题，回传编号没有意义，只会无谓地扩大响应契约；
   5xx 带上，用户才能把编号报给管理员。对外文案仍是通用文案，未泄露内部细节。

### 9.2 验证矩阵（含一处必须说明的「测不了」）

| 环节 | 验证方式 | 结果 |
| --- | --- | --- |
| 响应头始终回传 | e2e DEM-12 | ✅ `x-request-id` 非空 |
| 合法入参被原样透传 | e2e DEM-12（带自定义头请求） | ✅ 响应头与日志都出现该值 |
| 非法入参被丢弃 | e2e DEM-12（含空格 / 500 字符）+ 单测（换行、制表符、非 ASCII） | ✅ 均被替换为新生成的 UUID |
| 编号确实落到日志 | 读服务端 stdout | ✅ 见 §9.3 |
| 4xx 不扩大响应契约 | e2e DEM-12 + 单测 | ✅ 响应体不带 `requestId`（仅响应头携带） |
| 5xx 带上编号 | 单测（直接调过滤器 + 桩 host） | ✅ `error.requestId` 存在，且内部错误文案未外泄 |

**含换行的编号在 e2e 里测不了**：`fetch`（undici）自己就拒绝含换行的请求头，根本发不出去。
但「客户端会拦」不能成为省掉服务端校验的理由 —— 上游网关或 `curl` 都可能把原始字节透传过来。
因此换行/控制字符那几条改由**单测**覆盖（`backend/test/request-id.test.js` 中标 ★ 的用例），
e2e 只测 `fetch` 发得出去、但服务端同样该拒绝的值（含空格、超长）。

### 9.3 一个真实的日志样本

```
[HTTP] GET /api/requirements → 200 4.5ms rid=e2e-muv03wsv-rid
```

`e2e-muv03wsv-rid` 是 e2e 脚本自己传进来的值（不是服务端生成的 UUID）——
这说明「客户端传入的编号被原样沿用并落到日志」这条链路真的通了，
而这正是「用户报编号 → 管理员 grep 日志」能成立的前提。

同一批日志里还有 401 / 403 / 404 / 409 / 412 / 422 / 428 各种状态码，**每一行都带 rid**，
因此按编号能一次拿到该请求的完整上下文。

## 十、P1 第三项（E2 详情 / 历史分页）的落地验证（2026-10-05）

对应《后端架构审核与CI排查报告》§5.1 的 E2。

### 10.1 要解决的是什么

报告开篇指出读路径有 **2 处会随数据量线性恶化**的无界查询。E1 解决了列表，E2 解决另一处：
`detail()` 会把该需求的**全部**提交与**全部**事件一次性返回。

其中 `events` 是真正会无界增长的那个 —— 每次状态变更（创建 / 编辑 / 开始 / 提交 / 验收 / 退回）
都会追加一条，一个长期活跃的需求会积累几百上千条。`submissions` 的数量等于重提次数，由人的
行为决定，实际上界很低，但仍然给它一个上界：**不设上界的数组迟早会变成事故**。

### 10.2 做法与三个易错点

| 改动 | 说明 |
| --- | --- |
| `detail()` 的事件 | 默认返回**最近 50 条**（`?eventsLimit=` 可调，上限 200）；倒序取 N+1 再翻回升序 |
| `detail()` 的提交 | 固定返回**最近 20 次** |
| 截断可见 | 回传 `eventsTotal` / `eventsHasMore` / `eventsLimit` 与 `submissionsTotal` / `submissionsHasMore` |
| `/history` | 完整时间线，按事件的 `seq` 游标分页（默认 50 / 上限 200） |
| 前端 | 被截断时如实显示「仅显示最近 N 条（共 M 条）」，不把截断藏起来 |

**易错点 1：截断必须可见。** 只加 `take` 而不回传总数，界面就会把「最近 50 条」显示成「全部 50 条」——
数据没丢，但**用户以为没丢**，这比丢数据更难发现。e2e 专门断言 `eventsLimit=1` 时**总数仍是真实的 7**，
而不是返回数 1。

**易错点 2：详情取的必须是「最近」N 条。** 倒序取窗口再翻回升序，很容易在 `slice` / `reverse`
的顺序上写错，表现是「时间线少了最新几条」—— 数据量小时完全看不出来。e2e 的断言是
「详情窗口的最后一条 `seq` 等于全量时间线的最后一条」。

**易错点 3：两类游标不能混用。** 列表游标编码 `(createdAt, id)`、时间线游标编码 `seq`。
混用必须报 422 而不是静默把 `createdAt` 当 `seq` 用 —— 那会让分页悄悄错位。单测里有一条
★ 用例专门断言两者互不通用。

### 10.3 为什么时间线游标用 `seq` 而不是 `(createdAt, id)`

`requirement_event` 上有一个天然的好游标：`seq` 在**单个需求内单调递增**（由命令管道分配）。
它比 `(createdAt, id)` 更合适：

- 单调整数天然有序，**不存在「同一毫秒」的稳定性问题** —— E1 必须靠决胜键解决的那个问题，这里根本不存在；
- 只有一个字段，比较条件简单（`seq > cursor`）。

代价是它只适用于「同一个需求内」，跨需求分页不成立。而时间线恰好天然是需求内的，因此合适。

| 端到端 | ✅ **93/93**（新增 DEM-13 共 18 项） |

## 十一、P1 第四项（E4 登录并发闸门）的落地验证（2026-10-05）

对应《后端架构审核与CI排查报告》§5.1 的 E4。

### 11.1 要解决的是什么

报告 §3.4 指出：密码校验用 `bcryptjs`（**纯 JS 实现**）—— 这是 Dockerfile 里的刻意决策，
为的是避开原生模块编译、保证 `docker compose up --build` 一次成功。代价是它比原生实现
慢约 3~5 倍，且**在 Node 单线程上烧 CPU**。cost=10 时单次校验数十至上百毫秒；并发登录会
互相争抢同一个事件循环，**进而拖慢所有其它请求**（不只是登录）。

所以闸门做的不是「让登录更快」，而是**把故障域收窄**：

| | 改动前 | 改动后 |
| --- | --- | --- |
| 登录洪峰 | 事件循环被占满 → **全站变慢**（不可预期） | 登录排队或快速失败 → **其它接口不受影响**（可预期） |

### 11.2 三处设计取舍

1. **只罩 `bcrypt.compare`，不罩整个登录流程。** 数据库查询是 I/O 且便宜，并已有连接池兜底
   （`connection_limit`）。把便宜的部分也塞进闸门只会降低吞吐，不额外保护任何东西。
2. **排队但队列有上限。** 「超出则排队」不能是无限排队 —— 那只是把问题从 CPU 挪到内存，
   洪峰下会 OOM。队列满 → 立即 **503 + `Retry-After: 1`**；快速失败比「排很久最后超时」对
   调用方更友好。用 503 而非 429：这是**服务端容量**信号，不是针对某个调用方的配额
   （429 留给按账号/IP 的限流，即 P2 的 S7）。
3. **释放时把许可直接交给队首，而不是先还回池子。** 否则「刚到的请求」会与「已经等了很久的
   请求」抢同一个许可，等待时间变得不可预期。直接交接保证 FIFO，也让等待时间有上界。

另外，默认并发数用 `os.availableParallelism()` 而不是 `os.cpus().length`：容器里后者返回
**宿主机**核数，会无视 `--cpus` / cgroup 配额 —— 那正好会把闸门开到超过实际算力的位置，
与这个改动的目的相反。

### 11.3 一处**没有**拿到端到端实证的地方

闸门语义由 12 条确定性单测覆盖，但「**真实饱和 → 503**」这条端到端路径**没能测成**。

**尝试**：把服务以 `LOGIN_CONCURRENCY=1 / LOGIN_QUEUE_LIMIT=1` 启动，并发打 8 次登录。

**结果**：`4 × 200 + 4 × 500`，而那 4 个 500 **全部是数据库错误**：

```
FATAL: could not open file "base/24576/2600": Permission denied   (42501)
Can't reach database server at `127.0.0.1:5433`                    ← 数据库随后整体不可达
```

也就是说，**沙箱内的便携版 PostgreSQL 在并发登录下会崩溃**（本次会话已第 3 次复现）。
数据库一崩，请求在**到达闸门之前**就 500 了，饱和条件根本构造不出来。把排队超时压到 1ms
重试一次，结果相同 —— 因为请求被数据库拖成了串行到达，彼此不重叠。

**能确认的**：闸门本身工作正常 —— 服务端日志里出现了
`WARN [LoginGate] 登录闸门已满，请求进入队列（在途 1/1，排队 0）`，
说明饱和检测与入队逻辑被真实触发过；4 次成功登录说明正常路径没有被破坏。

**为什么接受这个缺口**：闸门的调度语义是**纯逻辑**，已被确定性单测钉死 —— 包括最容易写错的
「排队超时后必须出队」（不修这条，队列会逐渐泄漏直到所有人被 503，比没有闸门更糟）。
HTTP 映射（`Errors.overloaded()` → 503 + `Retry-After: 1`）由过滤器单测覆盖。剩下的唯一缝隙
（真实请求在真实饱和下返回 503）的风险，**低于**「为了测它而把 CI 弄得不稳定」的风险。
因此 e2e 只断言非饱和路径，并在此处如实标注这个缺口，而不是假装测过了。

**若要补齐**：需要一台 Docker 引擎可用的机器（`docker compose up` 起真实 PostgreSQL），
再跑同样的并发脚本；参数见 `.env.example` 的「登录并发闸门」一节。

## 十二、P2 首项（S6 liveness / readiness 拆分）与 S3 的落地验证（2026-10-05）

### 12.1 一次干净的停库对照实验

S6 的核心论点可以用一次实验直接证明。做法：停掉数据库，逐个探测三个端点。

| 端点 | 数据库可用 | **数据库不可用** | 语义 |
| --- | --- | --- | --- |
| `/api/health/live` | 200 | **200**（`probe=liveness`） | 进程活着 —— 它根本不碰数据库 |
| `/api/health/ready` | 200（`database=ok`） | **503**（`database=unreachable`） | 能接流量吗 —— 真实探测依赖 |
| `/api/health`（别名） | 200 | **503** | 与 readiness 同语义 |

实测输出（数据库已停）：

```
/health/live     → HTTP 200  {"ok":true,"probe":"liveness","service":"demand-acceptance-backend",...}
/health/ready    → HTTP 503  {"ok":false,"probe":"readiness",...,"database":"unreachable",...}
/health          → HTTP 503  {"ok":false,"probe":"readiness",...,"database":"unreachable",...}
```

恢复数据库并重启应用后，`/health/ready` 回到 200。

### 12.2 为什么这个差异不是形式主义

容器编排系统对两个探针的处置完全不同：

| 探针 | 失败时编排系统做什么 |
| --- | --- |
| liveness | **重启进程** |
| readiness | **摘掉流量，不重启** |

所以如果 liveness 里去查数据库，数据库一抖就会触发一轮**毫无意义的重启**：
重启既修不好数据库，又会切断正在处理的请求、重建连接池，让恢复更慢。
把依赖检查放进 liveness 是运维上最典型的自伤方式之一。

### 12.3 一个顺带观察到的细节

停库后即使数据库恢复，应用**仍返回 503** —— 因为 Prisma 连接池里的连接已经死了，
**必须重启应用进程**。这反过来印证了「readiness 只摘流量」的设计是对的：
真要让实例恢复服务，重启（由编排系统在进程真的不健康时执行）才是正确手段。

### 12.4 S3 的验证限度

`docker-compose.yml` 的 `web.depends_on` 由简写 `- api` 改为
`api: condition: service_healthy`，并由 `docker-compose config` 确认
（退出码 0、`web.depends_on.api.condition = service_healthy`、`container_name` 计数 0）。

但**没有真正起容器**验证「无 502 窗口」—— 本环境无 Docker 引擎。
这一项与 E3 的 nginx 改动同属「只做了结构校验」，补齐同样需要一台 Docker 可用的机器。

顺带把 `backend/Dockerfile` 的 HEALTHCHECK 从 `/api/health` 改为 `/api/health/ready`：
路径显式写出意图，避免读者以为它探的是 liveness。

## 十三、P2 后两项（C3 已应用迁移不可修改、C5 分支保护声明）的落地验证（2026-10-05）

### 13.1 C3：判定规则与「跳过 ≠ 通过」

**防的是什么**：迁移一旦被应用过，就已经写进某些库的 `_prisma_migrations` 表。回头改它会让
「迁移历史」与「实际库结构」**永久分叉** —— 跑过旧版的库不会重跑，新库跑的是改后的版本，
于是两个库结构不同，而双方都认为自己是对的。**本地重建库完全看不出这个问题**，所以只能靠门禁拦。

判定规则刻意选最简的一条，把误报压到零：

| 变更类型 | 判定 | 理由 |
| --- | --- | --- |
| `M` 修改 | ❌ 违规 | 这正是「改了已应用迁移」 |
| `D` 删除 | ❌ 违规 | 同上（重命名经 `--no-renames` 拆成 A+D，因此也被拦住） |
| `A` 新增 | ✅ 放行 | 新增正是迁移的**正常工作方式** |

**「跳过」必须与「通过」区分开**，而且**在 CI 里跳过 = 失败**：

| 情形 | 本地 | **CI** | 理由 |
| --- | --- | --- | --- |
| 未提供基准提交 | 跳过（退出 0） | ❌ **失败**（退出 2，给出修法） | CI 步骤会注入基准，拿不到就是步骤配错了 |
| 基准是全零 SHA（分支首次推送） | 跳过 | 跳过 | **唯一合法的跳过** —— 确实没有可比对的提交 |
| 基准在本地不可达（浅克隆） | 跳过 | ❌ **失败**（退出 2，提示加 `fetch-depth: 0`） | 门禁等于没接，却从外部看不出来 |

**为什么 CI 下跳过要失败**：本环境**读不到 job 日志**，所以「步骤绿了」必须等价于
「真的检查过了」。如果浅克隆导致脚本跳过、步骤照样绿，这条门禁就是**摆设**，
而且从外部完全看不出来。改成失败之后，**绿色本身就成了「它真的跑过」的证明** ——
这也是该 job 的 checkout 必须加 `fetch-depth: 0` 的原因（默认 depth 1 里没有基准提交）。

### 13.2 双向本地验证（用临时分支，测完即删）

| # | 情形 | 期望 | 实测 |
| --- | --- | --- | --- |
| 1 | 未提供基准提交（本地） | 跳过，退出 0 | ✅ 打印「未提供基准提交（命令行参数与 MIGRATION_BASE_REF 都为空）」 |
| 2 | 未提供基准提交（**模拟 CI**） | **失败，退出 2** | ✅ 打印 `::error::` 三条：门禁等于没接 / 原因 / 修法 |
| 3 | 基准是全零 SHA（本地与 CI） | 跳过，退出 0 | ✅ 打印「分支首次推送，没有可比对的前一个提交」 |
| 4 | 基准在本地不可达（**模拟 CI**） | **失败，退出 2** | ✅ 打印 `::error::` 并提示 checkout 需要 `fetch-depth: 0` |
| 5 | 基准正常、迁移无改动 | 通过，退出 0 | ✅ 「未发现对已应用迁移的修改或删除」 |
| 6 | **修改**已应用迁移并提交 | **违规，退出 1** | ✅ 打印 `M backend/prisma/migrations/0001_init/migration.sql` + 为什么是问题 + 应该怎么做 |
| 7 | **新增**迁移目录并提交 | 通过，退出 0 | ✅ 列为「新增（允许 —— 这正是迁移的工作方式）」 |

第 6、7 项用临时分支做（`tmp-c3-bad` / `tmp-c3-good`），测完删除分支并还原工作区，
确认 `git diff` 为空、迁移文件与 HEAD 逐字节一致。

### 13.3 C5：一处**无法从仓库自证**的验收项

`docs/代码审查标准与流程.md` §6.3.1 写明了 `main` 的 6 个 required status checks
（与 `.github/workflows/ci.yml` 的 6 个 job 一一对应），以及「Require branches to be up to date」
「禁止绕过」「禁止 force push」等配套约束。

但**仓库内的文档无法证明 GitHub 侧真的配置了**。这一点在文档里如实标注：
验收时应打开 `Settings → Branches → Branch protection rules` 逐条核对，
而不是「文档写了就算做了」。

文档里还写清了「为什么恰好是这 6 个」—— required checks 漏写一个，那条门禁就只是「建议」；
多写一个不存在的名字，GitHub 会永远等待一个永不出现的检查，**PR 永久卡住**。
因此 CI 增删 job 时这份清单必须同步更新。

## 十四、P2 第四项（S7 登录失败限流）的落地验证（2026-10-05）

### 14.1 与 E4 的分工：429 与 503 不是一回事

| | E4 并发闸门 | S7 失败限流 |
| --- | --- | --- |
| 管什么 | **容量** —— 在途 bcrypt 校验数 | **配额** —— 某来源连续失败次数 |
| 状态码 | **503** | **429** |
| 对客户端的含义 | 「服务端忙，稍后再试」 | 「你别再试了」 |

混用会让客户端无法判断该退避还是该停止，所以两者刻意分开。

### 14.2 位置很关键：限流是 `login()` 的第一步

限流检查在数据库查询与密码校验**之前**。两个好处：

1. 最便宜的拒绝路径 —— 封禁期间**连库都不查**（单测用桩 prisma 断言调用次数为 0）；
2. **不泄露账号是否存在** —— 不存在的账号同样会被限流，无法用 429 / 401 的差异去探测。

### 14.3 三条容易写错的边界（都有单测钉住）

| 边界 | 写错的后果 |
| --- | --- |
| 封禁**到期后计数必须清零** | 残留计数会让用户一解禁就又被立刻封禁 —— **永久锁死**，比不封禁更糟 |
| 封禁期间再失败**不得延长封禁** | 「越试越久」让封禁时间无上界，正常用户也等不到解禁 |
| 成功登录**必须清零** | 否则「错几次后成功」被累计，用户下次正常登录会莫名 429 |

写这三条时，我自己有**两条测试先写错了期望值**（把毫秒当成秒、把封禁起点算错），
修正的是测试而不是实现 —— 说明这几条边界确实不直观，值得用测试钉死。

### 14.4 手工确认的响应

```
第 1~5 次：HTTP/1.1 401 Unauthorized
第 6 次  ：HTTP/1.1 429 Too Many Requests
           Retry-After: 298
           {"error":{"code":"TOO_MANY_REQUESTS","message":"登录失败次数过多，请 298 秒后再试"}}
```

（`Retry-After` 为 298 是因为封禁 5 分钟、探测时已过了 2 秒 —— 秒数是**动态剩余时间**，
而不是固定的配置值。）

### 14.5 两条必须写下来的局限

1. **分布式攻击（多 IP 打同一账号）能绕开组合键** —— 每个 IP 各自计数。
   更强的做法是再叠一层「按 IP 计数、阈值更高」的规则；本项目规模下先不做。
2. **内存实现** —— 多副本部署时各副本各自计数，攻击者把请求分散到 N 个副本就有 N 倍尝试次数。
   强一致需落库（给登录路径加一次写）或引入 Redis（架构约束禁止）。
   本题规模（单实例）下内存实现足够 —— 但这是**需要写下来的取舍**，而不是默认它没问题。

键数量另有 **10000 的上限**并淘汰最久未用者 —— 否则海量随机账号能把内存撑爆，
那等于用限流本身做了一次 DoS。

### 14.6 为什么键是「账号 + IP」

| 键 | 问题 |
| --- | --- |
| 只按账号 | 攻击者随便失败几次就能把真实用户**锁在门外** —— 拿别人的账号当武器 |
| 只按 IP | 同一条出口 NAT 背后的所有人互相牵连；分布式攻击又能绕开 |
| **账号 + IP（采用）** | 攻击者必须同时命中同一个账号**且**来自同一个 IP；而且**锁无法被用来把别人关在门外** |

最后一条由单测与 e2e 各钉一次：单测断言「同账号不同 IP 互不影响」，
e2e 的 DEM-16 断言「探测账号被封不影响 alice 正常登录」。

## 十五、P1 最后一项（S4 entrypoint 错误可诊断）的落地验证（2026-10-05）

### 15.1 改造前的问题

```sh
if npx prisma migrate deploy; then ...
```

循环对**任何**失败都重试 60 次（60 × 2s = 120s）。而且 `if` 把 stderr 直接吞掉了 ——
运维只能看到「重试 60 次后放弃」，看不到真正的原因。若失败原因是迁移 SQL 本身有错，
重试 60 次毫无意义，只是把「立即失败」变成「等 120 秒后失败」，期间日志刷满无用的
重试信息，反而掩盖了真正的错误。

### 15.2 改造后的行为

| 改动 | 说明 |
| --- | --- |
| 捕获输出 | `output=$(npx prisma migrate deploy 2>&1) \|\| code=$?` —— `\|\|` 形式既能拿到退出码，又不会被 `set -e` 提前终止 |
| 打印完整错误 | **首次与最后一次**打印全文，中间只留一行 —— 既不丢信息也不刷屏 |
| 故障分流 | 迁移类错误（`P3018` / `P3005` / `P3009` / `P3019` / `P1012`、`syntax error`、`already exists`、`permission denied`）→ **立即退出**；其余（连接类）→ 重试 |
| 放弃时给提示 | 列出三步排查：`docker compose ps` → `DATABASE_URL` 的 host/port → 账号密码是否与 `POSTGRES_*` 一致 |

**兜底刻意选「不认识的一律重试」**：分类依赖 stderr 文本匹配（Prisma 只给 message、
没有结构化错误码），因此必然脆弱。默认重试意味着最坏情况只是退化成改造前的行为；
反过来兜底（默认立即失败）看起来更「干净」，但会在遇到没见过的连接类错误时
把正常的启动流程弄挂。

### 15.3 怎么在没有 Docker 的情况下验证

**办法**：不去起容器，而是**用一个假的 `npx` 驱动真实的 entrypoint 脚本**。
把桩程序放在 PATH 最前面，就能精确控制 `prisma migrate deploy` 的行为。

| 情形 | 桩的行为 | 期望 | 实测 |
| --- | --- | --- | --- |
| A | `P1001 Can't reach database server` | 重试到上限后放弃，退出码 1 | ✅ 打印完整错误 → 重试 3 次 → 给排查提示 |
| B | `P3018` + `syntax error` | **立即**失败，**不重试**，退出码 1 | ✅ 判定「迁移本身有问题」→ 立即退出，**未出现第 2 次** |
| C | 成功 | 继续 seed 并启动，退出码 0 | ✅ `node dist/seed.js` → `node dist/main.js` |
| D | 第 1 次失败、第 2 次成功 | 重试一次即通过，退出码 0 | ✅「迁移完成（第 2 次尝试）」→ 启动 |

**17 项断言全通过**，已固化为 `scripts/verify-entrypoint.mjs` 并接入 CI 的 backend job
（在 Linux runner 上跑，与容器内的执行环境一致 —— 同样是 POSIX sh）。

### 15.4 这个办法**不能**证明什么

它能证明「脚本在四种输入下的控制流正确」，**不能**证明「`docker compose up` 能起来」。
后者仍需一台有 Docker 引擎的机器。两者不要混为一谈 ——
把能验证的部分**真正验证掉**，把不能验证的部分**说清楚**，
比笼统地说「已验证」或「未验证」都更有用。

顺带确认了两个容易出事的细节：

- `docker-entrypoint.sh` 的行尾是 **LF**（`git ls-files --eol` → `i/lf w/lf`）。
  CRLF 会让容器内的 `sh` 直接报 `$'\r': command not found` —— 而且这个错误在本地
  用 Git Bash 跑是**看不出来**的。
- 通过 `sh -n` 的 **POSIX 语法检查**（shebang 是 `#!/bin/sh`，Debian slim 里是 dash，
  不能用 bash 专有语法）。

## 十六、P3 依赖漏洞扫描的接入与验证（2026-10-05）

### 16.1 这次扫描发现了 5 个真实漏洞

在此之前，仓库里**没有任何东西会告诉你依赖出了问题**。这次扫描立刻发现：

| 包 | 级别 | 漏洞 | 能否非破坏修复 |
| --- | --- | --- | --- |
| `deepmerge-ts`（经 `prisma` → `@prisma/config`） | **high** ×3（同一条公告） | 合并递归对象图时栈耗尽 | ❌ **不能** —— `@prisma/config` **精确锁定** `deepmerge-ts@7.1.5`（不是范围），唯一修复是升到 Prisma 8 |
| ~~`@vitest/mocker`（经 `vitest`）~~ | ~~moderate ×2~~ → **critical** | 路径穿越 / 任意文件读取；后升级为 `tinypool` 原型污染 → RCE | ✅ **已修复（2026-10-06）**：升到 vitest 5.0.3，`npm audit` 归零、77/77 测试全过 |

`npm audit fix`（非破坏）跑过，**无效**：`package.json` 与 lockfile 都没变，
漏洞仍在。这也验证了「非破坏修复不存在」这个判断。

### 16.2 为什么不能直接用 `npm audit --audit-level=high`

它会因为这 3 个 high 让 CI **永久变红**。而一条永远红的门禁等于没有门禁 ——
大家会习惯性地忽略它，**新出现的真漏洞也就一起被忽略了**。这比不接门禁更糟。

### 16.3 采用的形态：阻断 + 显式例外 + 腐化检测

`scripts/check-audit.mjs`：

- 任何 high / critical 不在白名单里 → **失败**
- 白名单条目必须写清「为什么可以接受」与「何时复核」
- 白名单条目**已经消失**（依赖被修好）→ **也失败**，提醒删掉它

最后一条很重要：没有它，白名单会越积越多，最后变成一张「什么都放行」的清单。

### 16.4 双向负例验证（否则这条门禁又是「永远绿」）

| 操作 | 期望 | 实测 |
| --- | --- | --- |
| 删掉 `deepmerge-ts` 的豁免 | 报「未豁免」并退出 1 | ✅ |
| 加一条不存在的豁免 | 报「白名单已过期」并退出 1 | ✅ |
| 恢复原状 | 退出 0 | ✅ |

### 16.5 两条豁免的理由（写进了代码里，不只是文档里）

- **`deepmerge-ts`**：漏洞需要合并**攻击者可控的递归对象图**，而 Prisma 的配置来自仓库内的
  静态文件；且 `prisma` 只在构建 / 容器启动时作为 CLI 使用，**不在 HTTP 请求路径上**。
  复核时机：Prisma 发布包含 `deepmerge-ts>=8` 的版本时。
- ~~**`vitest`**：仅开发期测试工具，不进生产镜像；修复需要破坏性升级，而它是 moderate。~~
  **（2026-10-06 已修复并移除豁免）** 漏洞后来升级为 critical，修复路径不变（仍是 vitest 5）。
  另外当时 Dependabot 里**忽略了 vitest 的大版本**，而修复恰好就是那个被忽略的大版本 ——
  该忽略已移除。教训：**豁免一条漏洞时，「严重级别」是会变的。**

### 16.6 一个实现上的坑：`npm audit` 的 `via` 有两种形态

`npm audit --json` 里每个漏洞的 `via` 数组里既有**对象**（具体公告）也有**字符串**
（「因为依赖了某个有漏洞的包」）。只按对象计数，否则同一条公告会沿着依赖链被
**重复报三次**（`deepmerge-ts` 一次、`@prisma/config` 一次、`prisma` 再一次）。

正确做法是先取每个包的「自有公告」，再沿 `via` 字符串做**传递闭包**把公告传播到下游包。
输出里因此能给出完整的受影响链：`deepmerge-ts → @prisma/config → prisma`。

另外加了一条安全网：high/critical 的包若最终没归到任何公告上，报成「未分类」让它显形 ——
不能因为 npm 换了输出结构就静默漏掉。

### 16.7 配套的 Dependabot

`.github/dependabot.yml`：每周一次，把 minor/patch **分组**成单个 PR
（逐个依赖开 PR 会让 5 个 PR 同时躺着、每个都重跑一遍 CI），major 不自动升
（`prisma` 的大版本会改动迁移语义 —— 本仓库刚吃过这个亏）。

**一处如实说明**：Dependabot 的**安全更新**（security updates）是仓库设置里的开关，
**不在这个配置文件里**。配置了版本更新不等于开了安全更新 —— 交付验收时应确认两者都已启用。

### 16.8 接入当天就抓到一个真问题（门禁判对了）

配置生效后 Dependabot **立刻**开出 PR（三个生态的运行都是 success，说明配置本身有效），
但其中 `@nestjs/common` 那个 PR 的 **CI 红了**。在本地完整复现：

```
npm error code ERESOLVE
While resolving: @nestjs/config@4.0.4
Found: @nestjs/common@12.1.2
Could not resolve dependency:
peer @nestjs/common@"^10.0.0 || ^11.0.0" from @nestjs/config@4.0.4
```

即 Dependabot 试图把 `@nestjs/common` **单独**升到 12.x，而 `@nestjs/core` 仍在 11.x、
`@nestjs/config` 的 peer 还写着 `@nestjs/common ^10 || ^11` —— 框架的「半升级」，
`npm ci` 必然失败（其余 5 个 job 都是被这一步级联带红的）。

**CI 判得对，是 Dependabot 的分组配置有缺陷。** 修法：

- 把 `@nestjs/*` 分成**一组**（`patterns: ['@nestjs/*']`），保证它们同版本一起升
- 把 `@nestjs/*` 的 **major** 加进 `ignore` —— 框架主版本要等**整个生态**跟上才能升，
  那不是自动 PR 能决定的事

复现方式（可重复）：`git fetch origin <dependabot 分支>` → 把 `backend/package.json`
与 `package-lock.json` 取到临时目录 → `npm ci`。不需要改工作区。

这件事本身就是「门禁有价值」的最好证据：它拦住了一个**真实的、会让构建失败的依赖变更**，
并在**合入之前**暴露了配置层面的缺陷。
